# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the **community edition** of Falang (AGPL-3.0-only, see `LICENSE`; contributions need a CLA, see
`CONTRIBUTING.md`). Design discussions happen in GitHub Issues/Discussions. Pointers of the form `ADR 00xx (private)`
refer to the maintainers' private architecture decision records — the rule or reason itself is always stated in place,
the pointer only says where the longer history lives.

## Workspace layout

npm workspaces monorepo. Node `>=24`, TypeScript 6, `"type": "commonjs"` throughout (except `playground` which is `"type": "module"`).

### Packages

**Core layer** (`packages/core/`):

- `agent` — `@falang/agent`: a stepwise, tool-calling LLM agent that edits a `Scheme` through its own existing actions (see ADR 0009 (private)) — vendor-neutral `ILlmClient` DI token, a `ScriptedLlmClient` mock, tool-schema generation from `NodesStack`/zod, `executeToolCall`, `AgentSession`, and `AgentModule` (requires `HistoryModule` registered on the same scheme). Knows no node kind by name; domains plug in via a multi-registered `IAgentContextProvider`. Since ADR 0036 (private): `AgentSession`'s constructor takes `defaultHomeScheme: Scheme | null` (not a required `Scheme`) and `IAgentRunOptions` gains `homeScheme?: Scheme` — `run()` resolves `options.homeScheme ?? defaultHomeScheme` (throwing if neither), capturing it once for the whole run so nothing about a host's active tab can retarget an in-flight turn; `IAgentDocumentResolver.resolve(documentId: string)` now takes a required id (an omitted `documentId` resolves to the run's captured home inside `AgentSession` itself, never reaching the resolver, and a resolver throw becomes a `fail()` tool result instead of a fatal run error); `createHomeOnlyDocumentResolver` takes a getter, not a fixed scheme. `AgentModule` is unchanged in shape but is now only the single-scheme convenience (playground, tests) — every real host constructs one project-level `AgentSession` itself instead. The system-prompt-building/finish-message/`documentId`-input helpers that used to live in `agent-session.ts` moved into `agent-session-internal.ts` to keep that file's size down. **Superseded the same day by ADR 0036's own amendments** (implemented): `defaultHomeScheme`/`homeScheme` are gone — the constructor's first param is `defaultScheme: Scheme | null` and the run option is `activeDocumentId?: string | null`, with no fail-fast document/`HistoryModule` requirement at all (a run can start, and `finish`, with zero documents — `tool-executor.ts`'s `executeFinish` is called directly, bypassing document resolution). The system prompt no longer embeds a tree or the node-kinds catalog — `IAgentContextProvider.describe` takes an `IAgentRunContext` (`activeDocumentId` + a lazy `getActiveScheme()`) instead of a resolved root node, and a generic `ProjectDocumentsContextProvider` (constructed over a plain document-list getter) now lives in this package, re-exported from `index.ts`. `onOpenDocument` fires before every resolved core call, not just first touch of a non-default document. Since ADR 0033 (private): the `finish` tool's argument is `message` (a direct first-person reply the user reads, not a report — `AgentSession.message`, renamed from `summary`), `describeToolCall` renders a short human-readable line per tool call for step-trace UI, `run()`'s `IAgentRunOptions.priorMessages` lets a caller carry a condensed prior conversation into a new run (`AgentSession` itself otherwise stays one-shot/stateless per call), and `chat-session.ts` holds the shared, dependency-free `IChatTurn`/`IChatSession`/`IChatSessionSummary`/`IAgentSessionStore` contract every host's session persistence implements. Since ADR 0034 (private): tool calls carry an optional `documentId`, resolved to a `Scheme` via a new `IAgentDocumentResolver` (`AgentModule`/`AgentSession` take one instead of being bound to a single `Scheme`; defaults to always the home scheme), with `onOpenDocument`/`onRunFinished` lifecycle hooks and a new `IAgentToolProvider` seam (`toolProviders?`) for host-defined tools — like `IAgentContextProvider`, entirely opaque to this package — that skip the focus/pause/undo-group treatment the built-in node tools get. Every mutating tool call now focuses the icon about to change and pauses ~300ms before applying it (`getFocusTargetId`), and undo grouping is one `HistoryStore` group per document touched during a run, not one group for the whole run. **Found and fixed (2026-09-22, a fourth real chat — agent burned ~23% of its step budget on retries and finished with a broken tree)**: a "build a Telegram guessing-game bot" run hit `Step limit reached` with a structurally broken result (two orphaned `while(true)` loops, no actual question/answer flow, references to never-created variables) — a log/export post-mortem found the failures clustered into distinct, fixable classes rather than random model error: (1) `documentId` dropped on 6 consecutive `insert_node` calls right after switching to a freshly created document; (2) `if` is a `childTuple`/fixed-slot node (its two `if-child` branches are auto-created by its factory, not addable by name) — `getAllowedChildNames` correctly returns `[]` for it, but the resulting "not allowed; allowed: " error gave no hint why, so the agent retried inserting directly under `if` four times before discovering (via a `get_tree` round trip) that it had to target the existing `if-child` ids instead; (3) `data` on an `if`/expression field is a source-code string, but the model sent a JSON boolean literal once and a `JSON.stringify`'d object twice elsewhere — the tool schema's `data: {}` gives zero type guidance up front; (4) an `arr-shift` call 3 times in a row missing its required `arr` field, most likely context-window pressure from the accumulated error messages above (a known, separately-flagged gap — see `AgentSession`'s own `DEFAULT_MAX_STEPS` doc comment on unpruned `messages`). Fixed on three fronts: a new `insert_nodes` tool (`packages/core/agent/src/insert-nodes.ts`) inserts a whole validated subtree — a node plus, recursively, its own `children`/`out` — in one call, atomically (nothing is applied if any node anywhere in the spec is invalid, and the error names the exact path, e.g. `node.children[1].children[0]`), collapsing what used to be many single-node round trips (and their per-call chance to drop `documentId`) into one; `@falang/mcp-core`'s `TNodeKindChildren` gained a `{ tuple: [...] }` case (replacing the opaque `'fixed-tuple'` string) so `get_node_kinds` now spells out a tuple parent's exact slot names/order/count instead of an empty list, and both `insert_node`/`insert_nodes` give a dedicated error (`describeNotAllowedError`, shared by both) pointing at the tuple's slot names and at `insert_nodes` when a caller targets a tuple parent directly; `insert_node`/`insert_nodes`' own tool descriptions now spell out the string-vs-object `data` convention explicitly, matching the pattern `NODE_KIND_NOTES` already established for node-kind semantics. Item (4) (context pruning) stays open, tracked where it already was. See ADR 0009 (private) new "Found and fixed (2026-09-22, a fourth real chat …)" section for the full trace. Since ADR 0035 (private): `insert_node`/`insert_nodes`/`set_out` all reject (before dispatching any command) a node placed or targeted at `children[0]` of its parent carrying an `out` — the same universal rule `@falang/scheme`'s `canHaveOut` enforces, checked here first so a violation comes back as a `fail()` tool result instead of `setOutNode`'s own thrown exception; `insert_nodes`' recursive `buildChildren` checks the rule at every position 0 across both its tuple and named-list branches. The three tool descriptions in `tools.ts` spell the rule out (including the fix — swap `if`'s branches and flip `meta.trueOnRight` — and an explicit warning against appending the out-type node as a plain last child instead, which compiles the same but draws no jump line).
  Since ADR 0034 (private) 2026-09-28 follow-ups: a call whose `ILlmToolCall.inputError` is set (arguments the client couldn't parse as JSON) runs nothing and gets that error back; `move_nodes` is validated like an insert (`validate-move-nodes.ts`); insert/move error texts live in `node-errors.ts`.
  Since ADR 0034 (private) 2026-09-27 "token budget" note: `IAgentNodeKindFilter` (`node-kind-filter.ts`, `IAgentSessionExtraOptions.nodeKindFilter`) trims what `get_node_kinds` lists (never validation) and its result is `{ nodeKinds, $defs?, note? }` (`$defs` since 2026-09-28, see `@falang/mcp-core`'s `describeNodeKinds`); `supersede-tool-results.ts` replaces every earlier `get_node_kinds` result in the conversation with a stub once it's called again, and (2026-09-28) an earlier `get_tree` of the same document once a later successful `get_tree` covers it — whole document, same `nodeId`, or a subtree containing the earlier `nodeId` (the `steps` trace keeps full results).
  Since ADR 0044 (private) (§4 step 0, 2026-09-29): `ILlmResponse.usage?: ILlmUsage` (`promptTokens`/`completionTokens`/`totalTokens`) and `AgentSession.usage` (observable `{ promptTokens, completionTokens, totalTokens, calls }`, summed across a run's steps, reset on every `run()`), `IChatTurn.usage?` in `chat-session.ts`.
  Since ADR 0047 (private): an `ask_user` tool (`ask-user.ts` — `ASK_USER_TOOL`, deliberately not in `AGENT_TOOLS`; offered per `resolveQuestionPolicy` from `IAgentRunOptions.allowQuestions`/`maxConsecutiveQuestions` (default 3)/`consecutiveQuestions`, a call in a run where it wasn't offered gets an error result) ends a run as `'awaiting-answer'` with `AgentSession.question` and `pendingMessages` (the run's full message list, to pass as the next run's `priorMessages`); the answer is the next run's request, built by `buildQuestionAnswerText` (`Answer: …`). `IChatTurn` gained `status: 'awaiting-answer'`, `question?` and `answersTurnId?`.
- `di` — `@falang/di`: thin wrapper over `tsyringe` adding typed symbol tokens.
- `debug` — `@falang/debug`: the debugger protocol (`IDebugAdapter`, `TDebugEvent`, `IDebugMap`, see ADR 0021 (private)) plus `FakeDebugAdapter`; dependency-free on purpose so compilers, `backend` and `runner` can import it without React/MobX.
- `dto` — `@falang/dto`: schema/DTO layer for the flow-diagram node model. `validate-function-name.ts` (2026-09-22) exports `isValidFunctionName`/`FUNCTION_NAME_PATTERN` (English, camelCase — `^[a-z][a-zA-Z0-9]*$`, e.g. `myFunctionName`) and `FUNCTION_LIKE_DOCUMENT_TYPES` (`'function'`/`'trigger-function'`) — a real bug found live: the in-app workflow agent created a `trigger-function` document with a Cyrillic, spaced name (a user asked it to build a Telegram bot), which `@falang/workflow-compiler`/`@falang/logic-constructor`/app-arduino's compiler all splice verbatim into a real function identifier with zero sanitization. Enforced at the interactive creation/rename entry points only — the workflow client's `ProjectTree`/`NewTriggerModal` UI and `DocumentToolProvider`'s `create_document`/`create_trigger_document` agent tools, `DocumentsService.create`/`update` (the one chokepoint both REST and the two `mcp-shared-tools.ts` MCP tools that bypass `ValidationPipe` funnel through), and both desktop apps' `ProjectTree` UI + `DesktopProjectStore`/`ArduinoProjectStore` stores + `@falang/desktop-mcp`'s `handleCreateDocument`/`handleRenameDocument` — deliberately **not** inside `@falang/desktop-project-fs`'s `createDocument`/`renameDocument` themselves or `@falang/mcp-core`'s `validateDocument`, since those are also the mechanism `@falang/desktop-project-converter` replays a legacy (pre-monorepo) project's own, already-real, often-PascalCase function names through on migration — gating there broke 4 real converter fixture tests (`DrawFood`/`ObjectCreation`/`TestBreak`/`Test1`/`ArrSum`) by retroactively rejecting names that predate this rule and already compile fine. Scope is deliberately narrow: only `function`/`trigger-function` documents, not `objects-structure`/`enum-structure`/`external-api-structure` (app-sketch's `logic` project type compiles those to struct names too via `@falang/logic-constructor` — the same latent bug, left as a known, undone follow-up). **Found and fixed (2026-09-22, from the same real chat)**: `INodeConfig.documentRootOnly` (`types.ts`) marks a node kind as valid only as a document's own `root`, never nested — set on the root entry of every shared document-root builder (`functionCfg`/`mindTreeCfg`/`countourNodeConfig` in `nodes/`) and on workflow's `triggerFunctionNodesGroup[0]`. `createZodUnion` (`zod-utils.ts`) now builds a filtered `statementUnion` for every `children: true` container instead of reusing the unfiltered "any node in the stack" union, closing a real gap the in-app agent hit live: `function`/`trigger-function` share one `NodesStack` (ADR 0002 (private)) so a `function-body`'s `children: true` used to accept a whole `trigger-function` root nested inside it. See ADR 0034 (private) "Found and fixed (2026-09-22, second real chat run …)" section. Since ADR 0035 (private): `createZodUnion` also adds a universal `.check()` (not `.refine()`, to stay a `discriminatedUnion`-compatible `ZodObject`) to every validator whose config declares a children policy at all (`children: true`, a named array, or `childTuple`), rejecting a parsed node whose `children[0]` carries an `out` (break/continue/return/throw) — matching the renderer's own long-standing `SkewerStore.hasOutError`/`isFirst` behavior, which never distinguished a branch from a plain sequential body or a loop. Enforced on the parent's own validator (a shared child config like `if-child` is reused for every slot and can't know which one it occupies), so it also gates `NodesStack.parseNode`/`parseDocument` for every caller — `@falang/mcp-core`'s `set_document`/`create_document` and `@falang/scheme`'s runtime parsing alike — with no separate per-caller implementation. A first-drafted, narrower `firstChildIsMainPath`-style flag scoped to branching kinds only was considered and dropped (see the ADR's "Considered and rejected") once it was clear the renderer draws no such exception. Since ADR 0044 (private) (§4 step 0): `zod-utils.ts` casts its two `z.discriminatedUnion(...)` results to `z.ZodUnion` (type-only) so the package type-checks against both the lockfile's zod 4.3.6 and zod 4.6.x — the registry spike had found the 4.6 typings reject the previous code.

`buildNodeKindsCatalog` is built on it, so every `get_node_kinds` host returns that shape. `getAllowedChildNames`'s `children === true` case now excludes `@falang/dto`'s `documentRootOnly` kinds (2026-09-22 fix, see ADR 0034 (private) "Found and fixed (second real chat run …)" section) — a `children: true` container no longer advertises/accepts a whole document-root node kind (e.g. `trigger-function`) as one of its own children just because both share a `NodesStack`. ## Architecture

### `@falang/dto` — node model

The domain is a tree of typed nodes. `INode` is the runtime shape; `INodeConfig` is the _declaration_ of a node kind (name, optional zod `data` schema, children policy, mods/out flags, factory).

Children policy is one of:

- `children: true` — any node from the stack.
- `children: ['nameA', 'nameB']` — array whose members must be one of the listed names.
- `childTuple: ['header', 'body', 'footer']` — fixed positional tuple. Advanced TS types in `types.ts` (`NodeFromConfigItem`, `TupleChildren`, `NodesFromConfig`) derive a discriminated union of concrete node types from a config list.

Higher-level builders in `src/nodes/` (`action`, `cycle`, `ifCfg`, `switchCfg`, `functionCfg`) return arrays of `INodeConfig` representing a group of related kinds (e.g. `functionCfg` emits `function`, `function-header`, `function-body`, `function-footer`).

`NodesGroup` wraps a config list (`hasName`, `is`, `factory`, `getConfig`). `NodesStack` aggregates groups, enforces globally-unique names, and — crucially — builds a runtime `zod` discriminated union (`zod-utils.ts`) for `parseNode`/`parseDocument`. A missing/unknown child name at stack construction throws. When adding a new node config, wire its children names to entries that already exist in the same stack.

`defaultFactory` synthesizes a new node instance from an `INodeConfig` when the config has no custom `factory` — it is what `NodesStack.factory(name)` falls back to.

### `@falang/di` — DI tokens

Re-exports `tsyringe`, plus `createSchemeToken<T>(name)` (a branded `symbol`) and `resolveService(token, container)`. `reflect-metadata` is imported once here so consumers don't have to.

### `@falang/scheme` — editor runtime

Entry point: `schemeFactory({ infra, modules, document })` in `src/scheme/scheme-factory.ts`. It:

1. Creates a child `tsyringe` container off the root `container`.
2. Instantiates `Scheme` (`src/scheme/scheme.ts`) — holds the container, `SchemeInfrastructure`, MobX stores (`rootNode`, `icons`, `nodes`), the event bus, and the command bus.
3. If a `document` is passed, parses it through `infra.structure.parseDocument`, converts nodes into `NodeStore` instances via `createNodeStoreFromNode`, and syncs icons.
4. Registers base DI tokens (`TOKEN_SCHEME`, `TOKEN_CSS_CLASSES`, …) then calls `registerModules()` + `initializeModules()` on every passed `IModule`.

`SchemeInfrastructure` bundles a `NodesStack` with an icons-config map keyed by node name (shape, block view, icon config). The icons config comes from caller-provided React/emotion components under `src/shapes/` and `src/icons/`.

**Stores.** Observable state lives in MobX classes under `src/store/` and `src/scheme/`:

- `NodeStore` mirrors a DTO node with observable `data`, `meta`, `children`, `mods`, `out`, `parent`.
- `SchemeNodesStore` / `SchemeIconsStore` index nodes and icons by id.
- View-model stores (`SelectionStore`, `MousePositionStore`, `ViewPositionStore`, `BlockEditorStore`, etc.) are registered as container-scoped services and resolved via tokens in `di-tokens.ts` (or via the `useService(token)` React hook on top of `ContainerContext`).

**Actions → events.** Mutations live in `src/actions/` (`insertNode`, `deleteNode`, `moveNodes`, `setData`, `setMeta`, `setOutNode`). Each mutates stores inside `runInAction` (often implicitly through the command bus) and fires a typed event via `scheme.events.fireEvent(EVENT_*, payload)` from `scheme-events.ts`.

**Command bus with priorities.** `SchemeCommandsService` dispatches commands to listeners registered at five priority levels (0–4, high → low, see `TCommandListenerPriority`). A listener returning `true` stops propagation. This is how modules intercept or augment actions. Concretely, `dispatchCommand` drains priority 4 first down to priority 0 last, so a priority-4 listener always gets to intercept (and stop) before a default-priority (0) one runs — see `icons-transfer`'s own comment on this ("above … below") and the read-only guards below, which rely on it.

**Read-only mode.** `schemeFactory({ readOnly: true })` (or `new Scheme({ readOnly: true, ... })`) builds a scheme with `isEditing` observable starting `false`. This blocks: the inline editor (click/double-click no longer start editing, `init-editor-handlers.ts`), the icon/valence-point context menus (`register-context-menu-handlers.ts`), and the six mutation commands (`CMD_INSERT_NODE`/`CMD_DELETE_NODE`/`CMD_MOVE_NODES`/`CMD_SET_DATA`/`CMD_SET_META`/`CMD_SET_OUT`) via a priority-4 guard per command registered in `registerSchemeCommands` that returns `true` (stopping propagation) whenever `!scheme.isEditing`, so the real (default-priority) handler never runs regardless of registration order. Already-`isEditing`-aware code (`valence-points.service.ts`, `icons-transfer.service.ts`, `block-resize.service.ts`, `pseudo-block.cmp.tsx`, `skewer.cmp.tsx`) needed no change. Pan/zoom, selection (`focusNode`/`SelectionStore`), `CssClassesStore`, `ExecutionPositionModule` and `DebuggerModule`'s highlight all keep working — none of them go through the mutation commands. Every host's `*SchemeFactoryParams` (`functionalSchemeFactory`/`objectsStructureSchemeFactory`/`enumStructureSchemeFactory`/`externalApiStructureSchemeFactory` in `@falang/typescript-scheme`, `functionalSchemeFactory`/`mindTreeSchemeFactory` in `@falang/text-scheme`, `codeFunctionalSchemeFactory` in `@falang/simple-code-scheme`, `workflowFunctionalSchemeFactory` in `@falang/workflow-scheme`) already extends `Omit<ISchemeFactoryParams, …>` and forwards `...props` straight into `schemeFactory` — `readOnly` reached every one of them for free, no per-factory edit needed. See ADR 0025 (private) "Implementation notes (package B …)".

**First-child `out` is forbidden, everywhere** (ADR 0035 (private)). The visual language draws a skewer's `children[0]` continuing the enclosing scheme's main path straight down (`SkewerStore.isFirst`, starting `true` for every skewer and only ever cleared by `update-threads-child-positions.ts` for a non-first thread) — an `out` (break/continue/return/throw) there renders as `hasOutError`'s red box regardless of whether the parent is a branch, a plain sequential body, or a loop. `utils/can-have-out.ts`'s `canHaveOut(scheme, id)` is the one shared predicate (`false` when the node's own config has no `haveOut`, or when it's `children[0]` of its parent); `setOutNode` (`actions/set-out-node.ts`) throws when asked to _set_ (not clear) an out `canHaveOut` rejects. `if`/`while`'s own branch-direction flags (`IfIconStore.trueOnRight`/`WhileIconStore.trueIsMain`) are `@computed` getters over `dataNode.meta`, both defaulting `false` — matching every compiler's own default rather than the icon's old, disagreeing hardcoded `true`; a shared `utils/build-switch-true-false-menu.ts`'s `buildSwitchTrueFalseMenu` toggles the flag via `CMD_SET_META` (merging into existing `meta`, never replacing it). `IconStore.getMeta()` (previously registered but never called) now feeds `utils/get-dto.ts`'s `getNodeStoreDto`/`getDto` through a new optional `scheme` parameter, so an icon's computed meta default (e.g. `if`'s `trueOnRight`) is folded into the persisted DTO even for a node with no `meta` key yet — callers that still call `getNodeStoreDto` with one argument keep the old, defaults-free behavior.

**Project module** (`src/modules/project/`) manages the project context within the editor — `ProjectService` holds the current project's id/name/type and a tree directory structure via `TreeDirectoryStore`.

**Debugger module** (`src/modules/debugger/`, ADR 0021) — `DebugSessionStore` is project-level (one per project, owns the `IDebugAdapter`, holds breakpoints keyed by document/node id — never in a node's `meta`); `DebuggerModule` is per scheme and takes that shared store plus the scheme's `documentId`, adding breakpoint dots (a scheme layer), a context-menu toggle (only if `ContextMenuModule` is present), `CMD_TOGGLE_BREAKPOINT`, and a `debug-current` block class + `scrollToNode` pan that follow the paused location. Breakable = `isStatementIcon` (parent has the `Skewer` flag). The antd panel lives in `@falang/antd`'s `ant-debug-panel`; hosts embed `DebugPanel` in their own right-hand `Sidebar`. Keyboard shortcuts and breakpoint persistence are host concerns.

**Version-diff module** (`src/modules/version-diff/`, ADR 0025) — `VersionDiffModule({ diff: INodeTreeDiff, side: 'left' | 'right' })` marks a static `@falang/versioning` diff onto one side of a split read-only diff view with `diff-added`/`diff-removed`/`diff-modified`/`diff-moved` block classes (green/red/amber/blue) via `CssClassesStore` — applied once in `initialize()` (the diff never changes across the module's lifetime; a new comparison builds a fresh pair of schemes), cleared in `dispose()`. `left` marks `removedIds`+`modifiedIds`+`movedIds`, `right` marks `addedIds`+`modifiedIds`+`movedIds` (a node both modified and moved gets both classes on its side). The pure helper `changeIdsForSide(diff, side)` returns the ordered, deduplicated list of ids worth stepping through (top-level removed/added plus every modified/moved id, in `diff.changes` order) for a "next/previous change" control built on the existing `scrollToNode`.

**Icons-transfer module** (`src/modules/icons-transfer/`, ADR 0027) — moving icons. Two gestures share one `IconsTransferService` (registered as an instance, it holds the `Scheme`) and one selection model (a contiguous range inside one `IIconWithList` parent, marked with the `selected` block class — deliberately not `SelectionStore`, which is the `focusNode` line-highlight selection): the click-based **transfer mode** (`DEFAULT_MODES.TRANSFER`: click an icon, a second click on the same skewer extends the range, click a valence point) and, in `start` mode, plain click / Shift-click range selection plus **drag-and-drop** (mouse-down on an icon, a move past `DRAG_START_THRESHOLD` enters the private `ICONS_DRAGGING_MODE_NAME` mode — registered without an icon, like `block-resize`'s — a `pointer-events: none` `IconsDragLayer` draws a dashed ghost of the selection + all descendants' shapes following the cursor, mouse-up drops onto `ValencePointsService.selectedValencePoint`). Both paths reuse `filterValencePoints` (installed as a valence-points filter) to decide where a drop is allowed and dispatch the same `CMD_MOVE_NODES` — `scheme.nodes`/`scheme.icons` are never touched during a drag. The command handlers (`init-icons-transfer-handlers.ts`) are thin wrappers around `mouseDown`/`mouseMove`/`mouseUp`/`mouseLeave`/`iconClicked`/`schemeClicked`, so `icons-transfer.test.ts` drives the service without a DOM. Requires `ValencePointsModule` on the same scheme.

**History module** (`src/modules/history/`) is the canonical example of a module. It registers `HistoryStore` scoped to the container and subscribes to the mutation events to push inverse operations onto an undo/redo stack; `history.back()` / `history.forward()` replay them. Any new cross-cutting feature should follow this pattern: implement `IModule` (`register` for DI bindings, `initialize` for event/command wiring, `dispose` to clean up), then pass an instance via `schemeFactory({ modules })`.

**Icons / geometry.** `checker.ts` centralizes type-narrowing of icons by bitmask `IconFlags` (`isWithChildren`, `isWithSkewer`, `isCycle`, `isFunctionBody`, …). Layout code lives in `src/skewer/` (vertical chains), `src/threads/` (horizontal branching), and `src/shapes/` (SVG primitives).

**Test harness.** `packages/core/scheme/test-utils/` exposes `getTestInfrastructure()` + `getTestEmptyDoc()` — use these in new tests instead of rebuilding a stack from scratch. See `src/modules/history/history.test.ts` for the canonical setup pattern (`beforeEach` builds infra, calls `schemeFactory`, tears down with `scheme.dispose()`).

### TypeScript scheme — `block-elements/` vs `blocks/`

`packages/typescript/scheme/src/block-elements/` holds small, reusable editing widgets (a MobX store + React component pair) shared across multiple node blocks — distinct from `src/blocks/`, which holds one full `IBlockConfig` per node kind. Most are internal (consumed via relative imports only, not exported from the package's `index.ts`) — the exception is `block-elements/code/`, see below.

- `block-elements/code/` — `CodeModelStore` (monaco `ITextModel` wrapper; supports a `hiddenPrefix` of lines hidden from the user but visible to the TS language service, e.g. scope `declare`s) + `CodeModelEditingComponent` / `CodeViewComponent` / `ExpressionEditorCellComponent`. `CodeModelStore` and `ExpressionEditorCellComponent` (plus `ExpressionBlockEditorStore` from `monaco/scope/` and `TsSelect` from `cmp/`) **are** exported from the package's `index.ts` — `@falang/workflow-scheme`'s `IntegrationActionEditorStore` (integration action node fields) consumes them across the package boundary to get real Monaco-backed expression fields and struct-aware selects, the same way any in-package block does. `monaco/get-monaco.js` (the shared Monaco bootstrap: TS worker wiring, overflow-widgets host) and `monaco/use-code-theme.js` are exported the same way — `@falang/simple-code-scheme`'s `block-elements/raw-code/` (see "Simple-code domain" above) reuses them for its own, deliberately non-validating Monaco models instead of reimplementing Vite worker plumbing. `getMonaco()` also exports `setMonacoLibVariant('full' | 'portable')` — `monaco.typescript.typescriptDefaults` is one global instance for the whole window, so which `lib.d.ts` every `'typescript'`-language model type-checks against is a host-level choice (call once per opened project, before building its schemes), not a per-editor one. `'full'` (the default, `monaco/lib.ts`, unchanged) is the real JS/TS surface. `'portable'` (`monaco/lib-portable.ts`) is a hand-written, deliberately minimal replacement declaring only what `@falang/logic-constructor`'s `cpp`/`golang`/`rust`/`sharp` adapters actually support (see ADR 0019 (private)) — `Math` trimmed to the 9 methods every adapter's `CALL_MAP` whitelists, `Array`/`String` trimmed to `length`+indexing, no `Promise`/`JSON`/`RegExp`/`Symbol`/`Map`/`Set`/`Date`/free functions at all — so the editor never suggests or accepts syntax that would only fail later with `UnsupportedConstructError` at export. `@falang/desktop-app-sketch`'s `DesktopProjectStore` selects `'portable'` for `project.type === 'logic'` (`'full'` otherwise) and `@falang/desktop-app-arduino`'s `ArduinoProjectStore` always selects `'portable'` (every Arduino sketch compiles to C++ only, through the same `@falang/logic-constructor` statement compiler); the workflow product never calls it, staying on `'full'`, since its `function`/`trigger-function` documents compile to real, executed TS.
- `block-elements/new-variable/` — `NewVariableStore`, a plain text input (no monaco) for fields that _declare_ a new identifier rather than an expression. Validates TypeScript identifier syntax and rejects reserved words (`validate-variable-name.ts`), and checks uniqueness against a caller-supplied `getScopeNames()` callback (typically `collectScopeVariables(dataNode).map(v => v.name)`).

### TypeScript scope tracking (`monaco/scope/`)

- `collectScopeVariables(node: NodeStore): IScopeVariable[]` now lives in `@falang/typescript-common` (`src/scope/collect-scope-variables.ts`, moved there per ADR 0009 so it's importable from node tests without pulling in `monaco-editor` through `@falang/typescript-scheme`'s index); `packages/typescript/scheme/src/monaco/scope/collect-scope-variables.ts` is kept as a one-line re-export so existing in-package imports are unchanged. It walks up from a node, collecting every scope-introducing sibling declared _before_ it in each enclosing scope: `create-var` (explicit `TVariableInfo`), plus the array ops that assign a result — `arr-pop`/`arr-shift` (new variable typed as the array's _element_ type) and `arr-slice` (new variable typed as the _array_ type itself). The latter two only know a raw `typeof`-based type query, not a structured DTO type, so `IScopeVariable['type']` is `TVariableInfo | IRawVariableType` (`{ type: 'raw', expression, constant? }`, see `scope-variable.ts`); `build-hidden-scope-code.ts` renders a raw type verbatim instead of running it through `variableInfoToTsType`.
- `array-element-type.ts` builds those raw type queries from an `arr`-field's expression text: `buildArrayTypeExpression('someobj[x+1].someArr')` → `"typeof someobj[number]['someArr']"` (dots become `['prop']`, bracket contents become `[number]` — verified against `tsc`: TS's `typeof` type-query grammar disallows a dot immediately after a bracketed index). `buildArrayElementTypeExpression` appends one more trailing `[number]` to peel the array type down to its element type.
- `buildHiddenScopeCode(variables, typesRegistry)` renders `collectScopeVariables`'s output into `declare const/var …` lines prepended (invisibly, via `hiddenPrefix`) to a monaco model; struct types are resolved from `TypesRegistryStore` and emitted as `interface` declarations.
- The array-op node blocks were split by whether they need a value typed in or produce one: `arr-op-returning` (arr-pop, arr-shift — result field uses `new-variable`) and `arr-op-input` (arr-push, arr-unshift — value field uses `code-model`, hidden-prefixed with the array's element type) replaced the old single `arr-op` block. `arr-insert`'s `insertArr` field is hidden-prefixed with the array's own type (matching element type, since the items are spread in).
