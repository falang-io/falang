<p>
  The workflow engine ships as open source, and you can run the whole thing locally — the fastest way to try it
  out. You'll need <a href="https://www.docker.com/" target="_blank">Docker</a> and
  <a href="https://kind.sigs.k8s.io/" target="_blank"> kind</a> (Kubernetes in Docker) installed: every running
  scenario executes in its own pod on a local k8s cluster, the same mechanism production uses.
</p>

#### Quick start
<ol>
  <li>
    Create the local kind cluster:
    <pre><code>./scripts/kind-dev-setup.sh</code></pre>
    The script is idempotent — safe to re-run, for example after changing the runner's code, to rebuild and reload
    its image into the cluster.
  </li>
  <li>
    Copy <code>.env.example</code> to <code>.env</code> at the repo root. For a clean local run you don't need to
    change anything — every secret (<code>JWT_SECRET</code>, <code>CREDENTIALS_ENCRYPTION_KEY</code>, etc.) has a
    dev-only default baked in (the bundled compose file also sets <code>SEED_DEFAULT_ADMIN=true</code>; the backend itself defaults it to <code>false</code>). With <code>NODE_ENV=production</code> the backend refuses to start unless <code>JWT_SECRET</code>, <code>DB_PASSWORD</code> and <code>CREDENTIALS_ENCRYPTION_KEY</code> are set to non-default values of at least 32 characters.
  </li>
  <li>
    Bring the stack up:
    <pre><code>docker compose -f docker-compose.workflow.yml up --build</code></pre>
  </li>
  <li>
    Open <code>http://localhost:5175</code> and log in as
    <code> admin</code>/<code>admin</code> (auto-seeded the first time the backend boots), or register a new
    account from the login page.
  </li>
  <li>Create a project, then inside it a folder and a "Function" document: give the function a name and a body.</li>
  <li>
    Click "Build &amp; Run" in the toolbar. This compiles every function in the project and creates a pod in the
    kind cluster to run them — shown under a task-queue name like <code>workflow-dev-&lt;projectId&gt;</code>
    (displayed in the toolbar next to the status dot, and via <code>kubectl -n workflow get pods</code>).
  </li>
  <li>
    Open the function and choose <b>Dev → Run function</b> in the toolbar (it asks for the function's parameters, if any): the icon it is
    executing lights up on the canvas and a side panel shows its status and history. You can also start an execution
    with the Temporal admin CLI:
    <pre><code>{`docker compose -f docker-compose.workflow.yml exec temporal-admin-tools \\
  temporal workflow start --task-queue workflow-dev-<projectId> --type <functionName> \\
  --workflow-id demo-1 --input '{}'`}</code></pre>
    Watch it run in the Temporal Web UI: <code>http://localhost:8080</code>.
  </li>
  <li>
    "Publish" promotes the current code to the stable version (a shared task queue,
    <code> workflow-&lt;projectId&gt;</code>) — the "Versions" modal lets you roll back ("Activate") or retire
    older versions ("Stop runner"). The version tagged "Current" is the one new runs and triggers go to and the one
    "Start" brings up; a rollback stays in effect across Stop/Start and while an idle runner sleeps.
  </li>
</ol>

#### What's in the stack
<p><code>docker-compose.workflow.yml</code> brings up:</p>
<ul>
  <li>a self-hosted <b>Temporal</b> server (version 1.32, with its own Postgres, a one-shot schema job and a job creating the <code>default</code> namespace), its admin CLI and web UI;</li>
  <li>a separate Postgres database for the <b>backend</b> (projects, folders, documents, users);</li>
  <li>the <b>backend</b> — stores projects, compiles functions, and manages starting/stopping runner pods via the Kubernetes API;</li>
  <li>the <b>client</b> — the web scheme editor (the Admin app is served at <code>/admin</code>);</li>
  <li>
    <b>MinIO</b> — S3-compatible object storage for <a href="../files/">files</a> (console at
    <code>http://localhost:9001</code>);
  </li>
  <li><b>media</b> — the ffmpeg service behind the <a href="../media/">Media</a> integration;</li>
  <li>
    <b>activepieces</b> — a helper service backing part of the integrations catalog (see
    <a href="../integrations/"> Integrations</a>).
  </li>
</ul>
<p>
  Every published scenario runs not as a process inside the backend's own container, but as its own pod in
  Kubernetes — which is why the local kind cluster is needed.
</p>

#### Isolating projects in Temporal
<p>
  By default (<code>TEMPORAL_TENANT_ISOLATION=shared</code>) every project's workflows run in Temporal's single
  <code>default</code> namespace with no authorization — fine for local development and for an instance whose
  projects all belong to people you trust. A runner pod runs a project's own code, so on a multi-tenant instance
  switch on <code>per-project</code> mode: each project gets its own namespace (<code>falang-&lt;projectId&gt;</code>),
  runner pods authenticate with a short-lived JWT valid for that namespace only, and cross-namespace commands are
  disabled on the server. Start the stack like this (use the same private key every time):
</p>
<pre><code>{`export TEMPORAL_JWT_PRIVATE_KEY="$(openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048)"
export PROJECT_TOKEN_SECRET="$(openssl rand -hex 32)"
TEMPORAL_SERVER_CONFIG=server.yaml TEMPORAL_TENANT_ISOLATION=per-project \\
  docker compose -f docker-compose.workflow.yml up --build`}</code></pre>
<p>
  The Temporal server fetches the public key from the backend's internal port
  (<code>/internal/temporal/jwks.json</code>), so a key rotation needs only a backend restart. In this mode the
  Temporal web UI on port 8080 can no longer log in; use the admin CLI instead, which talks to Temporal's internal
  frontend (port 7236, never published to the host):
</p>
<pre><code>{`docker compose -f docker-compose.workflow.yml exec temporal-admin-tools \\
  temporal workflow list --namespace falang-<projectId>`}</code></pre>
<p>
  The backend variables behind this mode:
</p>
<ul>
  <li>
    <code>TEMPORAL_TENANT_ISOLATION</code> — <code>shared</code> (default) or <code>per-project</code>. In
    <code>per-project</code> mode the backend refuses to start without <code>TEMPORAL_JWT_PRIVATE_KEY</code>, and at
    startup it checks that Temporal really rejects requests without a token or with a token it can't verify (it
    refuses to start if it doesn't, because the isolation would be worth nothing).
  </li>
  <li>
    <code>TEMPORAL_JWT_PRIVATE_KEY</code> — an RSA private key in PKCS#8 PEM format (RS256 signing). Optional:
    <code>TEMPORAL_JWT_KEY_ID</code> (defaults to the key's thumbprint), <code>TEMPORAL_JWT_PREVIOUS_PUBLIC_KEY</code>
    (the old public key, published next to the new one while you rotate), <code>TEMPORAL_JWT_TTL_SECONDS</code> (pod
    token lifetime, default 3600; pods renew it on their own).
  </li>
  <li>
    <code>PROJECT_TOKEN_SECRET</code> — the key the per-project tokens runner pods use to talk to the backend are
    derived from (in production, at least 32 characters and not a default value; the same value on every backend
    replica).
  </li>
  <li>
    <code>TEMPORAL_NAMESPACE_RETENTION_DAYS</code> — how long finished executions are kept in each project's namespace
    (default 7). <code>TEMPORAL_TLS=true</code> — if your Temporal frontend terminates TLS.
  </li>
  <li>
    <code>RUN_JOURNAL_RETENTION_DAYS_DEV</code> / <code>RUN_JOURNAL_RETENTION_DAYS_PROD</code> — how many days the
    <a href="../run-journal/">run journal</a> keeps entries of dev-stand and published runs (both default 14; the
    journal outlives the engine's own run history).
  </li>
</ul>
<p>
  A deleted project's namespace is removed by the backend about a day after the project is deleted. Switching an
  existing instance from <code>shared</code> to <code>per-project</code> does not move old executions out of
  <code>default</code>; the backend pauses the schedules it left there, and republishing a project starts it in its own
  namespace.
</p>

#### A known quirk
<p>
  On the very first <code>docker compose up</code> after the <code>falang-workflow-network</code> network is
  (re)created, the backend container sometimes fails to attach to the second network (<code>kind</code>) in time —
  its logs show a steady stream of <code>getaddrinfo EAI_AGAIN app-postgres</code> errors. One command fixes it:
</p>
<pre><code>docker compose -f docker-compose.workflow.yml restart backend</code></pre>
<p>It doesn't recur once both networks are actually attached.</p>

#### Public and internal ports
<p>
  The backend listens on two ports. The public one (<code>PORT</code>, 4000 in the compose files) serves the
  application API and is the only one to publish through a reverse proxy or ingress. The internal one
  (<code>INTERNAL_PORT</code>, default 3001) serves only <code>/internal/*</code> — the API used by runner pods, the
  ActivePieces service and the media service; the public port answers 404 for those paths. Never expose the internal
  port to the internet: point <code>BACKEND_INTERNAL_URL</code> of those services at it (inside a cluster, a ClusterIP
  Service).
</p>

#### Behind a proxy, CORS, rate limits, request sizes
<p>
  Set <code>TRUST_PROXY</code> when the backend sits behind a reverse proxy or load balancer, otherwise every client
  looks like the proxy's IP and the per-IP rate limits below hit all users at once. It takes a number of hops (for
  example <code>1</code>), <code>true</code>, or a list of IPs/CIDRs/<code>loopback</code>; the default
  is <code>false</code>. <code>CORS_ORIGINS</code> is a comma-separated list of allowed browser origins; when unset the
  origin of <code>CLIENT_PUBLIC_URL</code> is used, and with neither the API is open to any origin (a warning is logged).
  The backend sends security headers on every response and rejects bodies over 256 KB, except the endpoints that
  legitimately take large JSON (project import, document writes, the AI agent and MCP, up to 15 MB) — the answer is
  <code>413</code>.
</p>
<p>
  A built-in, per-replica rate limiter (login, account e-mails, webhooks, builds/runs/publishing and AI agent calls, plus
  a general per-IP limit) answers <code>429</code> with <code>Retry-After</code>. <code>RATE_LIMIT_ENABLED=false</code>
  turns it off and <code>RATE_LIMIT_MULTIPLIER</code> scales all limits; the internal port and <code>/health</code> are
  never limited. Resource caps per account (<code>MAX_PROJECTS</code>, <code>MAX_DEV_PODS</code>,
  <code>MAX_STORED_VERSIONS</code>, <code>MAX_OWNER_FILES_BYTES</code>, <code>MAX_SCHEDULES</code>) are defaults that
  an admin can override per user in the Limits dialog. Schedules cannot fire more often than every
  <code>SCHEDULE_MIN_INTERVAL_SECONDS</code> (60), and every workflow execution is stopped after
  <code>WORKFLOW_EXECUTION_TIMEOUT</code> (default <code>30 days</code>; <code>off</code> disables it). Activities
  without their own retry policy retry at most 5 times.
</p>

#### Local mode without Docker
<p>
  If you only want to try the engine on one machine, you can skip Docker, kind and Postgres entirely. Run
  <code>npm install</code> and then <code>npm run start-local</code> in the repository root: a single Node process
  starts the backend with an embedded database, keeps files on disk, runs every scenario as a child process and serves
  the editor from the same port (<code>http://localhost:4000</code>, login <code>admin</code>/<code>admin</code>). The
  Temporal dev server is started alongside it; the <code>temporal</code> CLI is downloaded automatically if it is not
  installed. Everything is stored in <code>~/.falang-flow</code> — back up the whole folder including
  <code>secrets.json</code>. ActivePieces integrations and the media service are not available in this mode, and
  inbound webhooks need a tunnel to the public port.
</p>

#### Production images
<p>
  The default targets of <code>docker/backend.Dockerfile</code> and <code>docker/client.Dockerfile</code> are for
  development (the client runs the Vite dev server). For a real deployment build <code>--target production</code>:
  the backend then runs as the unprivileged <code>node</code> user, and the client is the static build served by
  unprivileged nginx on port 8080 with security headers and a Content-Security-Policy (see
  <code>docker/client-nginx/README.md</code> for its environment variables).
</p>

#### Logs and metrics
<p>
  <code>LOG_FORMAT=json</code> makes the backend write one JSON object per line (level, timestamp, context, message and,
  inside an HTTP request, <code>requestId</code> — the same value the response carries in <code>x-request-id</code>; an
  incoming <code>x-request-id</code> of up to 128 safe characters is reused). The default is human-readable text.
  <code>LOG_LEVEL</code> optionally filters: one level (<code>warn</code> means warn and above) or a comma-separated
  list. <code>GET /internal/metrics</code> on the internal port exposes Prometheus metrics (process, Node.js, HTTP
  requests by route template, builds, runner pods, AI agent calls); there is no authentication, so keep that port
  private.
</p>
