<p>
  Workflow-движок распространяется как open source, и его можно полностью запустить локально — это самый быстрый
  способ его попробовать. Понадобятся установленные <a href="https://www.docker.com/" target="_blank">Docker</a> и
  <a href="https://kind.sigs.k8s.io/" target="_blank"> kind</a> (Kubernetes in Docker): каждый запущенный сценарий
  выполняется в собственном поде локального k8s-кластера — тем же механизмом, что и в боевом окружении.
</p>

#### Быстрый старт
<ol>
  <li>
    Создайте локальный kind-кластер:
    <pre><code>./scripts/kind-dev-setup.sh</code></pre>
    Скрипт идемпотентен — его можно перезапускать повторно, например после изменений в коде раннера, чтобы
    пересобрать и перезагрузить его образ в кластер.
  </li>
  <li>
    Скопируйте <code>.env.example</code> в <code>.env</code> в корне репозитория. Для чистого локального запуска
    можно ничего не менять — у каждого секрета (<code>JWT_SECRET</code>, <code>CREDENTIALS_ENCRYPTION_KEY</code> и
    т.д.) есть значение по умолчанию для разработки (dev-compose также задаёт <code>SEED_DEFAULT_ADMIN=true</code>; сам backend по умолчанию использует <code>false</code>). При <code>NODE_ENV=production</code> backend не запустится, пока <code>JWT_SECRET</code>, <code>DB_PASSWORD</code> и <code>CREDENTIALS_ENCRYPTION_KEY</code> не заданы нестандартными значениями длиной не менее 32 символов.
  </li>
  <li>
    Поднимите стек:
    <pre><code>docker compose -f docker-compose.workflow.yml up --build</code></pre>
  </li>
  <li>
    Откройте <code>http://localhost:5175</code> и войдите как
    <code> admin</code>/<code>admin</code> (учётная запись создаётся автоматически при первом запуске backend'а)
    либо зарегистрируйте новый аккаунт со страницы входа.
  </li>
  <li>Создайте проект, затем в нём — папку и документ типа «Функция»: задайте имя и тело функции.</li>
  <li>
    Нажмите «Build &amp; Run» на панели инструментов. Это скомпилирует все функции проекта и создаст под в
    kind-кластере для их выполнения — под очередью задач вида <code>workflow-dev-&lt;projectId&gt;</code> (её имя
    отображается на панели инструментов рядом с индикатором статуса, а также командой
    <code> kubectl -n workflow get pods</code>).
  </li>
  <li>
    Откройте функцию и выберите <b>Тестовый стенд → Запустить функцию</b> на панели инструментов (если у функции есть параметры, их спросят): иконка,
    на которой идёт выполнение, подсвечивается на холсте, а боковая панель показывает статус и историю. Запустить
    выполнение можно и через CLI администратора Temporal:
    <pre><code>{`docker compose -f docker-compose.workflow.yml exec temporal-admin-tools \\
  temporal workflow start --task-queue workflow-dev-<projectId> --type <functionName> \\
  --workflow-id demo-1 --input '{}'`}</code></pre>
    Ход выполнения можно наблюдать в Temporal Web UI: <code>http://localhost:8080</code>.
  </li>
  <li>
    Кнопка «Publish» переводит текущий код в стабильную версию (общую очередь задач
    <code> workflow-&lt;projectId&gt;</code>) — в модальном окне «Версии» доступны откат («Активировать») и
    остановка более старых версий («Остановить раннер»). Версия с меткой «Текущая» — та, на которую идут новые
    запуски и триггеры и которую поднимает «Запустить»; откат сохраняется после Стоп/Запуск и пока простаивающий
    раннер спит.
  </li>
</ol>

#### Из чего состоит стек
<p><code>docker-compose.workflow.yml</code> поднимает:</p>
<ul>
  <li>самостоятельно размещённый сервер <b>Temporal</b> (версия 1.32, с собственной базой Postgres, разовыми заданиями создания схемы и namespace <code>default</code>), его админ-CLI и веб-интерфейс;</li>
  <li>отдельную базу Postgres для <b>backend</b>'а (проекты, папки, документы, пользователи);</li>
  <li>
    <b>backend</b> — сервис, который хранит проекты, компилирует функции и управляет запуском/остановкой подов
    выполнения через Kubernetes API;
  </li>
  <li><b>client</b> — веб-редактор схем (приложение администратора открывается по адресу <code>/admin</code>);</li>
  <li>
    <b>MinIO</b> — S3-совместимое объектное хранилище для <a href="../files/">файлов</a> (консоль —
    <code>http://localhost:9001</code>);
  </li>
  <li><b>media</b> — сервис на ffmpeg для интеграции <a href="../media/">Медиа</a>;</li>
  <li>
    <b>activepieces</b> — вспомогательный сервис для части интеграций (см. <a href="../integrations/">Интеграции</a>).
  </li>
</ul>
<p>
  Каждый опубликованный сценарий выполняется не отдельным процессом внутри контейнера backend'а, а собственным
  подом в Kubernetes — именно поэтому нужен локальный kind-кластер.
</p>

#### Изоляция проектов в Temporal
<p>
  По умолчанию (<code>TEMPORAL_TENANT_ISOLATION=shared</code>) все workflow проектов выполняются в единственном
  namespace <code>default</code> Temporal без авторизации — этого достаточно для локальной разработки и для
  экземпляра, где все проекты принадлежат доверенным людям. Runner-под исполняет код самого проекта, поэтому на
  экземпляре с несколькими пользователями включите режим <code>per-project</code>: у каждого проекта свой
  namespace (<code>falang-&lt;projectId&gt;</code>), runner-поды аутентифицируются короткоживущим JWT,
  действительным только для этого namespace, а межнеймспейсные команды на сервере выключены. Запуск (ключ нужно
  держать одним и тем же между запусками):
</p>
<pre><code>{`export TEMPORAL_JWT_PRIVATE_KEY="$(openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048)"
export PROJECT_TOKEN_SECRET="$(openssl rand -hex 32)"
TEMPORAL_SERVER_CONFIG=server.yaml TEMPORAL_TENANT_ISOLATION=per-project \\
  docker compose -f docker-compose.workflow.yml up --build`}</code></pre>
<p>
  Публичный ключ Temporal берёт у backend на внутреннем порту (<code>/internal/temporal/jwks.json</code>), поэтому
  для смены ключа достаточно перезапустить backend. В этом режиме веб-интерфейс Temporal на порту 8080 войти
  не сможет; используйте админ-CLI — он ходит во внутренний frontend (порт 7236, на хост не публикуется):
</p>
<pre><code>{`docker compose -f docker-compose.workflow.yml exec temporal-admin-tools \\
  temporal workflow list --namespace falang-<projectId>`}</code></pre>
<p>
  Переменные backend'а, на которых держится этот режим:
</p>
<ul>
  <li>
    <code>TEMPORAL_TENANT_ISOLATION</code> — <code>shared</code> (по умолчанию) или <code>per-project</code>. В режиме
    <code>per-project</code> backend не запустится без <code>TEMPORAL_JWT_PRIVATE_KEY</code>, а при старте проверит,
    что Temporal действительно отклоняет запросы без токена и с токеном, который он не может проверить (если нет —
    backend откажется стартовать: такая изоляция ничего не стоит).
  </li>
  <li>
    <code>TEMPORAL_JWT_PRIVATE_KEY</code> — приватный RSA-ключ в формате PKCS#8 PEM (подпись RS256). Необязательные:
    <code>TEMPORAL_JWT_KEY_ID</code> (по умолчанию — отпечаток ключа), <code>TEMPORAL_JWT_PREVIOUS_PUBLIC_KEY</code>
    (прежний публичный ключ, публикуется рядом с новым на время ротации), <code>TEMPORAL_JWT_TTL_SECONDS</code> (срок
    жизни токена пода, по умолчанию 3600; поды обновляют его сами).
  </li>
  <li>
    <code>PROJECT_TOKEN_SECRET</code> — ключ, из которого выводятся токены проектов, с которыми runner-поды ходят в
    backend (в production — не короче 32 символов и не значение по умолчанию; на всех репликах backend'а одно и то
    же).
  </li>
  <li>
    <code>TEMPORAL_NAMESPACE_RETENTION_DAYS</code> — сколько хранятся завершённые выполнения в namespace проекта (по
    умолчанию 7). <code>TEMPORAL_TLS=true</code> — если frontend Temporal работает по TLS.
  </li>
</ul>
<p>
  Namespace удалённого проекта backend удаляет примерно через сутки после удаления проекта. Переключение
  существующего экземпляра с <code>shared</code> на <code>per-project</code> не переносит старые выполнения из
  <code>default</code>; расписания, оставшиеся там, backend ставит на паузу, а переопубликованный проект начинает
  работать в своём namespace.
</p>

#### Известная особенность
<p>
  При самом первом запуске <code>docker compose up</code> после (пере)создания сети
  <code> falang-workflow-network</code> контейнер backend'а иногда не успевает подключиться ко второй сети
  (<code>kind</code>) — в его логах будут постоянные ошибки вида <code>getaddrinfo EAI_AGAIN app-postgres</code>.
  Лечится одной командой:
</p>
<pre><code>docker compose -f docker-compose.workflow.yml restart backend</code></pre>
<p>Повторно эта проблема не возникает, пока обе сети не пересоздаются заново.</p>

#### Публичный и внутренний порты
<p>
  Backend слушает два порта. Публичный (<code>PORT</code>, в compose-файлах 4000) отдаёт API приложения — только его
  нужно публиковать через reverse proxy или ingress. Внутренний (<code>INTERNAL_PORT</code>, по умолчанию 3001) отдаёт
  только <code>/internal/*</code> — API для runner-подов, сервиса ActivePieces и медиа-сервиса; на публичном порту эти
  пути отвечают 404. Не открывайте внутренний порт в интернет: укажите его в <code>BACKEND_INTERNAL_URL</code> этих
  сервисов (внутри кластера — через ClusterIP Service).
</p>
