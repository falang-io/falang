# Commands and verification

## Commands

Run from the repo root unless noted.

- `npm test` — runs Vitest across all workspace projects (`vitest.config.root.ts` references `./packages/*/*`).
- `npm run test-e2e` — runs `@falang/workflow-e2e-tests` (Playwright) against `docker-compose.workflow-e2e.yml`, tearing the stack down after. Same stack `coverage:e2e` uses, without coverage instrumentation. Heavy (spins up the full e2e stack — Temporal, Postgres, WordPress, ActivePieces).
- `npm run test:headless-schemes` — plain-Node (`tsx`, no browser/bundler/vitest) smoke test that builds a `Scheme` with every product's real scheme factory (workflow incl. the magic node, typescript, text contour/mind-tree, every simple-code language), inserts a node, serializes and validates it; proves `@falang/{typescript,text,simple-code,workflow}-scheme` stay importable without a browser. `scripts/headless-agent-smoke.ts` (workflow; its in-memory store is `scripts/headless-workflow-store.ts`), `scripts/headless-json-files-smoke.ts` (workflow, ADR 0062's JSON file interface: write, validation error, `check_project` error, undo, compile — over the same store), `scripts/headless-code-agent-smoke.ts` (workflow with `agentInterface: 'code'`, ADR 0061 (private): file writes incl. a type error and its fix, an edit + undo, then compile + type-check) and `scripts/headless-desktop-agent-smoke.ts` (app-sketch `logic` + `simple-code-ts`, app-arduino with the bundled drivers) then run the real in-app agent session through the host factories against a scripted LLM and compile the result with the product's real compiler (`compileCppProject` / `generateCode` / `compileArduinoProject`, plus a real `arduino-cli compile --fqbn arduino:avr:uno` when the CLI and AVR core are installed — the bundled-driver sketch deliberately uses `hc-sr04`, which needs no extra Arduino library).
- `npm run start-local` — the workflow product on one machine without Docker (PGlite, disk files, process runners, the `temporal` CLI; ADR 0072 (private), package `@falang/workflow-local`). `npm run test-e2e:local` runs its end-to-end spec (`vitest.config.local-e2e.ts`).
- `npm run test-e2e:fast [-- --tier workflow|browser|all] [--with <services>] [--reuse-client] [--keep] [-- <filters>]` — the existing e2e suites (workflow tier + Playwright, one worker) against the local mode instead of the kind stack (`scripts/test-e2e-fast.ts`: mocks and `start-local` as child processes on free ports, the client built with `VITE_BACKEND_URL=same-origin` into `node_modules/.cache/falang-e2e-fast/client`; logs kept in a temp dir on failure or with `--keep`). No Docker; minutes instead of 15–25. Specs needing what the local mode lacks are skipped through `FALANG_E2E_MISSING` (`activepieces`, `media`, `mail`, `postgres-user-db`, `mysql-user-db`, `egress-proxy`, `temporal-isolation` — by default all but the last are provided by the started services; checked by `workflowE2eHas`/`describeIfStackHas`/`itIfStackHas` in `backend/src/test-utils/workflow-e2e-capabilities.ts` and `e2eHas` in `e2e-tests/tests/e2e-capabilities.ts` — mark a new spec that needs one of them). A quick check while working, not a replacement for `npm run test-e2e`: k8s pods, real Postgres, S3 and tenant isolation are only covered there. `--with a,b` (default `DEFAULT_SERVICES` in the script, one line per service) passes `--with`/`--test-mode` to the local-mode CLI, merges each started service's `testEnv` (status file `services`) into the test env and drops its capabilities from `FALANG_E2E_MISSING` (the union also has `postgres-user-db`/`mysql-user-db`).
- `npm run test-e2e-logic` — runs `@falang/logic-e2e-tests` (plain Vitest, but every test shells out to `docker` to build/run generated C++/Go/Rust/C# inside the pinned `logic-cpp-runner`/`logic-go-runner`/`logic-rust-runner`/`logic-sharp-runner` images — see ADR 0019 (private)). Excluded from plain `npm test`'s `vitest.config.root.ts` projects glob for that reason. Needs a working Docker daemon; the first run also builds the four images (slow).
- `npm run coverage` — `coverage:unit` + `coverage:services` + `coverage:e2e` + `coverage:merge` in sequence, ending with the combined report at `coverage/combined`; a failing unit or service test doesn't stop the e2e/merge steps (the run still exits non-zero). Heavy (spins up the full e2e stack — Temporal, Postgres, WordPress, ActivePieces) — use `coverage:unit` alone for a quick local check.
- `npm run coverage:unit` — Vitest only, with coverage (via `vitest-monocart-coverage` wrapped by `scripts/vitest-coverage-provider.mjs`, which drops modules compiled from memory under made-up filenames; writes and cleans only `coverage/unit`; always produces a report, even if a test file fails — `reportOnFailure: true`, see ADR 0012 (private)). Runs with `--maxWorkers=50% --testTimeout=120000 --hookTimeout=120000`: instrumentation roughly doubles the heavy compile tests' time, and a per-file `vi.setConfig`/per-test timeout still overrides these flags.
- `npm run coverage:e2e` — runs `@falang/workflow-e2e-tests` against `docker-compose.workflow-e2e.yml` with coverage instrumentation on (browser via Playwright CDP, `backend` + its build workers via `NODE_V8_COVERAGE` — set only here, through `BACKEND_V8_COVERAGE`, so a plain `test-e2e` collects nothing — and runner pods via their push to `InternalCoverageController`), writing raw coverage under `coverage/e2e-browser` and `coverage/e2e-node`. `scripts/coverage-e2e-dirs.sh prepare`/`finalize` (through a throwaway `alpine` container) clear both before the run and hand the root-owned, partly mode-600 output to the host user after it.
- `npm run coverage:services` — own Vitest suites of the standalone services `activepieces/` and `proxy/` (not workspace members; `npm ci` is run in a service without `node_modules`) with the root's monocart provider borrowed through `scripts/vitest.config.services.mjs` (no coverage dependency in their lockfiles), raw output in `coverage/services/<service>/raw` with repo-relative paths (`proxy/src/...`); clears `coverage/services` first, a failing suite doesn't skip the other service but the exit code is non-zero. Light; part of `npm run coverage`.
- `npm run coverage:logic` — optional, needs Docker, NOT part of `npm run coverage`: builds the four logic runner images and runs `@falang/logic-e2e-tests` (`test-e2e-logic`) with the unit run's provider (`scripts/vitest.config.logic.mjs`), raw output in `coverage/logic/raw`; clears `coverage/logic` first. Run it before `coverage:merge` to include logic-constructor compile-and-run coverage.
- `npm run coverage:merge` — merges `coverage/unit`, `coverage/e2e-browser`, and `coverage/e2e-node` (required) plus `coverage/services/{proxy,activepieces}/raw` and `coverage/logic/raw` (optional — included only when present, one log line names them; same readability check) into one report at `coverage/combined` (`scripts/merge-coverage.mjs`, via `monocart-coverage-reports`; rebases container `/app/…`, runner `file:///app/…` and Vite `@fs/app/…`/bare-filename source-map paths onto repo paths). Fails instead of writing a partial report when an input file is unreadable or when `e2e-node` has no file of the `backend` process itself (its `SIGTERM` hook never finished).
- Desktop release builds (ADR 0050 (private)) — `.github/workflows/desktop-release.yml` (manual `workflow_dispatch`, app `sketch`/`arduino`/`flow`/`all`) builds each app natively on ubuntu/windows/macos runners (x64, unsigned) and runs `npx tsx scripts/release/smoke-desktop-app.ts <sketch|arduino|flow> [--screenshot <png>]` against the packaged output (`flow` is its own sequence in `scripts/release/smoke-flow-app.ts`: boots the shell with a throwaway `FALANG_FLOW_USER_DATA`, checks the admin sign-in, imports a one-function project, builds and runs it through the staged backend, quits and looks for leftover processes; the others: bundled worker under the app binary in Node mode, the bundled MCP server over stdio — for `arduino` incl. the bundled drivers — and the app window; Linux needs a display, CI uses `xvfb-run`). Locally: `npm run prebuild:linux -w @falang/desktop-app-<app>` + `npm run build -w …` + `npx electron-builder --linux AppImage --x64 --publish never` in the app dir, then the smoke script (unset `ELECTRON_RUN_AS_NODE` first, see memory). Windows from Linux through Wine (the native `build:win` / CI `win` job is unchanged): `npm run build:wine -w @falang/desktop-app-<sketch|arduino|flow>` — its `prebuild:wine` hook is the `prebuild:win` one (flow: `build-flow-backend-dist.ts --platform win32 --arch x64`, which for a platform/arch other than the host's installs with `npm install --os/--cpu --ignore-scripts`, so `@esbuild`/`@swc` are the win32 packages), then `electron-vite build` + `scripts/release/electron-builder-wine.ts` (checks `wine` on `PATH`, `electron-builder --win --x64 --publish never`, `WINEDEBUG=-all`, no signing); output `dist/*-setup-<version>.exe` + `dist/win-unpacked`. macOS from Linux on a Mac reached over SSH (ADR 0050 (private); an Intel Mac, x64 native): `npm run build:mac-remote -w @falang/desktop-app-<sketch|arduino|flow>` (`scripts/release/build-mac-remote.ts`: syncs the `git ls-files -co --exclude-standard` tree to `FALANG_MAC_HOST` (default `mac`) `:~/${FALANG_MAC_DIR:-falang-build.noindex}` (the suffix keeps Spotlight out), `npm ci` when the lockfile changed, `prebuild:mac` + `build` + `electron-builder --mac --x64` with `NODE_OPTIONS=--max-old-space-size=4096` (the renderer build needs ~3 GB of heap), the smoke test (the SSH user must be logged in to the Mac's desktop), and copies `*.dmg`/`*.zip`/`*.blockmap`/`smoke-mac.png` back into the app's `dist/`; `--no-smoke` skips the test). `package-lock.json` must carry the other platforms' entries of `optionalDependencies` (rollup, `@swc/core`, …) — npm drops them when the lock is regenerated on Linux (npm/cli#4828), and `npm ci` on macOS/Windows then fails the vite build. The packaged exe runs under Wine in Node mode (`ELECTRON_RUN_AS_NODE=1 wine <app>.exe script.js`; Wine has no usable stdout pipe there — write results to a file). Every esbuild bundle that type-checks through `@falang/logic-constructor` (the MCP server, `app-arduino`'s compile worker, `app-sketch`'s export worker) ships TypeScript's `lib*.d.ts` next to itself (`scripts/release/copy-typescript-libs.ts`; `extraResources` copies the whole output directory) — `ts.createCompilerHost` looks for them in the executing file's directory, i.e. the bundle's, and without them every type check fails ("Cannot find global type 'Array'"); the smoke script's worker step compiles a real non-empty document so this regression fails CI. Products are FalangSketch / FalangDuino / FalangFlow (`productName`; appIds `io.falang.sketch`/`io.falang.duino`/`io.falang.flow`); artifact names carry no spaces: `<prefix>-<version>-<arch>.<ext>`, `<prefix>-setup-<version>.exe`, `<prefix>_<version>_amd64.deb` with prefix `falang-sketch`/`falang-duino`/`falang-flow` (= `deb.packageName`). Each `electron-builder.yml` has a `generic` `publish.url` (`https://download.falang.io/<sketch|duino|flow>`, `generateUpdatesFilesForAllChannels`), so every build also writes `latest*.yml`/`beta*`/`alpha*`; the `build:linux|mac|win` scripts pass `--publish never`. `scripts/release/feed.ts` (+ `feed-lib.ts`) puts a build on that static feed over rsync: `upload <app>` (versioned binaries into `<feed>/`, the update-info files into `<feed>/.staged/<version>/`; refused once the version is live), `promote <app> <version> [--notes] [--staging <%>] [--force]` (update-info files into `<feed>/` — installed apps see it from then on — and, for a stable version, `<feed>/latest/` stable-name symlinks + `version.json` for the download page), `status <app>`; feed dir and prefix come from `electron-builder.yml`; rsync over SSH as root: host `FALANG_DOWNLOAD_TARGET` (default `falang-io`, an ~/.ssh/config alias), site root `FALANG_DOWNLOAD_ROOT` (default `/projects/download.falang.io`), optional `FALANG_DOWNLOAD_SSH_KEY`, transport override `FALANG_DOWNLOAD_RSH`.
- `cd proxy && npm install && npm test` — the standalone egress proxy's own Vitest suite (not part of the root `npm test`; `cd activepieces && npm test` likewise for the ActivePieces adapter service).
- `npx oxlint` — lint (config at `.oxlintrc.json`; every category is `error`).
- `npm run format` — format all files with Prettier (config at `.prettierrc.json`: 120 print width, single quotes, trailing commas).
- `npm run format:check` — check formatting without writing changes; CI runs it. `.prettierignore` also skips `*.mdx` (Prettier's MDX 1 parser breaks Starlight pages), `.kimi-code/memory/` (its Markdown printer corrupts dense inline code), Astro's `.astro` dirs and the converter's old-app `test-fixtures`.
- `docker compose -f docker-compose.registry.yml up -d` / `down` — the local Verdaccio registry (`docker/verdaccio/config.yaml`: `@falang` scope only, no npmjs uplink, named volume `falang-registry-storage`); see `scripts/README-registry.md` and ADR 0044 (private).
- Production images (security audit P1-6): `docker/backend.Dockerfile --target production` (runs as `USER node`; the default target is unchanged) and `docker/client.Dockerfile --target production` (static `dist` served by unprivileged nginx on 8080 with a CSP and security headers, config in `docker/client-nginx/`, see its README "Production client image"; the default target is still the Vite dev server). The cloud overlay's client image is built from `private/`.
- `scripts/publish-snapshot.sh [--dry-run] [--allow-dirty] [--registry <url>] [--tag <tag>]` — publish every workspace package under `packages/*/*` (TypeScript sources, no build) to that registry as a time-ordered snapshot `0.<YYYYMMDD>.<HHMMSS>` (tag `dev`, commit recorded in `falangSnapshot`), from a throwaway worktree of `HEAD`; consumers use `.npmrc` `@falang:registry=http://127.0.0.1:4873/` and `npm update '@falang/*'`.
- `node scripts/prepare-publish-manifests.mjs [--dry]` — idempotent manifest hygiene (`license`, `"*"` for internal `@falang/*` specs, `files`, `@types/*` into `dependencies` where `src/` imports through them); re-run after adding a package.

Per-package:

- `npm test -w @falang/dto` / `npm test -w @falang/scheme` — run one package's Vitest suite (each uses the shared `vitest.config.ts`).
- `npm run check -w <package>` — type-check a package (`tsc --noEmit -p tsconfig.build.json`); every package under `packages/` has this script.
- `npm run stryker -w @falang/dto` — mutation tests (Stryker vitest runner). No config file is checked in; expect to add one before it runs.
- `npm run dev -w playground` / `npm run build -w playground` — Vite dev server / production build.
- `npm run dev -w playground-workflow` — Workflow editor dev server (port 5174).

Single test: `npx vitest run -c vitest.config.ts path/to/file.test.ts -t "test name"` from inside the relevant package.

Backend e2e harness on a real Postgres without Docker (ADR 0072 (private), 2026-10-31): `FALANG_TEST_DB=pglite-migrations npx vitest run -c ../../../vitest.config.ts src/**/*.e2e.test.ts --hookTimeout=120000` from `packages/workflow/backend` runs every `createTestApp`/tasks-harness suite on PGlite (Postgres 17 in WASM) with the schema built by the real `src/migrations/*.ts`; `FALANG_TEST_DB=pglite` uses `synchronize` instead; unset = the usual in-memory `better-sqlite3` (≈4× faster — PGlite boots per test). `test-utils/test-db-options.ts` + `queued-pglite-driver.ts` (one session, checkout queue, `timestamp` read as UTC) are the switch; `test-migrations.ts`/`test-entities.ts` are static lists (TypeORM's migrations glob can't load `.ts` under vitest). Fixtures must use real UUIDs for `uuid` columns — sqlite never checked.

**After every task: run `npm run lint` from the repo root, and run `npm run check -w <package>` for every changed package, fixing all errors before marking the task done.**

**At the end of each implementation phase (e.g. each phase of a multi-phase ADR, or any other logical chunk of work worth checkpointing): run the full test suite, both `npm test` (unit) and `npm run test-e2e` (e2e) — not just the tests touching that phase's files.**

**Before marking any task done, in every piece of work in this repository: check whether the change makes existing documentation stale, and update it if so.** This covers `AGENTS.md` and the relevant files under `.kimi-code/memory/`, package/service `README.md` files, the private ADRs.md`(append an "Implementation notes" section rather than rewriting the original decision — see existing ADRs for the pattern), and`site/docs`(the public docs site — both`en/`and`ru/`locales, see`site/docs/README.md`). Not every change touches documentation, but the check itself is mandatory, not optional.
