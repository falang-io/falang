# Core packages

**Core layer** (`packages/core/`):

- `agent` — `@falang/agent`: a stepwise, tool-calling LLM agent that edits a `Scheme` through its own existing actions (see ADR 0009 (private)) — vendor-neutral `ILlmClient` DI token, a `ScriptedLlmClient` mock, tool-schema generation from `NodesStack`/zod, `executeToolCall`, `AgentSession`, and `AgentModule` (requires `HistoryModule` registered on the same scheme). Knows no node kind by name; domains plug in via a multi-registered `IAgentContextProvider`. Since ADR 0036 (private): `AgentSession`'s constructor takes `defaultHomeScheme: Scheme | null` (not a required `Scheme`) and `IAgentRunOptions` gains `homeScheme?: Scheme` — `run()` resolves `options.homeScheme ?? defaultHomeScheme` (throwing if neither), capturing it once for the whole run so nothing about a host's active tab can retarget an in-flight turn; `IAgentDocumentResolver.resolve(documentId: string)` now takes a required id (an omitted `documentId` resolves to the run's captured home inside `AgentSession` itself, never reaching the resolver, and a resolver throw becomes a `fail()` tool result instead of a fatal run error); `createHomeOnlyDocumentResolver` takes a getter, not a fixed scheme. `AgentModule` is unchanged in shape but is now only the single-scheme convenience (playground, tests) — every real host constructs one project-level `AgentSession` itself instead. The system-prompt-building/finish-message/`documentId`-input helpers that used to live in `agent-session.ts` moved into `agent-session-internal.ts` to keep that file's size down. **Superseded the same day by ADR 0036's own amendments** (implemented): `defaultHomeScheme`/`homeScheme` are gone — the constructor's first param is `defaultScheme: Scheme | null` and the run option is `activeDocumentId?: string | null`, with no fail-fast document/`HistoryModule` requirement at all (a run can start, and `finish`, with zero documents — `tool-executor.ts`'s `executeFinish` is called directly, bypassing document resolution). The system prompt no longer embeds a tree or the node-kinds catalog — `IAgentContextProvider.describe` takes an `IAgentRunContext` (`activeDocumentId` + a lazy `getActiveScheme()`) instead of a resolved root node, and a generic `ProjectDocumentsContextProvider` (constructed over a plain document-list getter) now lives in this package, re-exported from `index.ts`. `onOpenDocument` fires before every resolved core call, not just first touch of a non-default document. Since ADR 0033 (private): the `finish` tool's argument is `message` (a direct first-person reply the user reads, not a report — `AgentSession.message`, renamed from `summary`), `describeToolCall` renders a short human-readable line per tool call for step-trace UI, `run()`'s `IAgentRunOptions.priorMessages` lets a caller carry a condensed prior conversation into a new run (`AgentSession` itself otherwise stays one-shot/stateless per call), and `chat-session.ts` holds the shared, dependency-free `IChatTurn`/`IChatSession`/`IChatSessionSummary`/`IAgentSessionStore` contract every host's session persistence implements. Since ADR 0034 (private): tool calls carry an optional `documentId`, resolved to a `Scheme` via a new `IAgentDocumentResolver` (`AgentModule`/`AgentSession` take one instead of being bound to a single `Scheme`; defaults to always the home scheme), with `onOpenDocument`/`onRunFinished` lifecycle hooks and a new `IAgentToolProvider` seam (`toolProviders?`) for host-defined tools — like `IAgentContextProvider`, entirely opaque to this package — that skip the focus/pause/undo-group treatment the built-in node tools get. Every mutating tool call now focuses the icon about to change and pauses ~300ms before applying it (`getFocusTargetId`), and undo grouping is one `HistoryStore` group per document touched during a run, not one group for the whole run. **Found and fixed (2026-09-22, a fourth real chat — agent burned ~23% of its step budget on retries and finished with a broken tree)**: a "build a Telegram guessing-game bot" run hit `Step limit reached` with a structurally broken result (two orphaned `while(true)` loops, no actual question/answer flow, references to never-created variables) — a log/export post-mortem found the failures clustered into distinct, fixable classes rather than random model error: (1) `documentId` dropped on 6 consecutive `insert_node` calls right after switching to a freshly created document; (2) `if` is a `childTuple`/fixed-slot node (its two `if-child` branches are auto-created by its factory, not addable by name) — `getAllowedChildNames` correctly returns `[]` for it, but the resulting "not allowed; allowed: " error gave no hint why, so the agent retried inserting directly under `if` four times before discovering (via a `get_tree` round trip) that it had to target the existing `if-child` ids instead; (3) `data` on an `if`/expression field is a source-code string, but the model sent a JSON boolean literal once and a `JSON.stringify`'d object twice elsewhere — the tool schema's `data: {}` gives zero type guidance up front; (4) an `arr-shift` call 3 times in a row missing its required `arr` field, most likely context-window pressure from the accumulated error messages above (a known, separately-flagged gap — see `AgentSession`'s own `DEFAULT_MAX_STEPS` doc comment on unpruned `messages`). Fixed on three fronts: a new `insert_nodes` tool (`packages/core/agent/src/insert-nodes.ts`) inserts a whole validated subtree — a node plus, recursively, its own `children`/`out` — in one call, atomically (nothing is applied if any node anywhere in the spec is invalid, and the error names the exact path, e.g. `node.children[1].children[0]`), collapsing what used to be many single-node round trips (and their per-call chance to drop `documentId`) into one; `@falang/mcp-core`'s `TNodeKindChildren` gained a `{ tuple: [...] }` case (replacing the opaque `'fixed-tuple'` string) so `get_node_kinds` now spells out a tuple parent's exact slot names/order/count instead of an empty list, and both `insert_node`/`insert_nodes` give a dedicated error (`describeNotAllowedError`, shared by both) pointing at the tuple's slot names and at `insert_nodes` when a caller targets a tuple parent directly; `insert_node`/`insert_nodes`' own tool descriptions now spell out the string-vs-object `data` convention explicitly, matching the pattern `NODE_KIND_NOTES` already established for node-kind semantics. Item (4) (context pruning) stays open, tracked where it already was. See ADR 0009 (private) new "Found and fixed (2026-09-22, a fourth real chat …)" section for the full trace. Since ADR 0035 (private): `insert_node`/`insert_nodes`/`set_out` all reject (before dispatching any command) a node placed or targeted at `children[0]` of its parent carrying an `out` — the same universal rule `@falang/scheme`'s `canHaveOut` enforces, checked here first so a violation comes back as a `fail()` tool result instead of `setOutNode`'s own thrown exception; `insert_nodes`' recursive `buildChildren` checks the rule at every position 0 across both its tuple and named-list branches. The three tool descriptions in `tools.ts` spell the rule out (including the fix — swap `if`'s branches and flip `meta.trueOnRight` — and an explicit warning against appending the out-type node as a plain last child instead, which compiles the same but draws no jump line). Since ADR 0049 (private): `insert_nodes` fails on any spec (nested or out) carrying a `mods` key, pointing at `set_document` — mods are not an agent node-tool concern in v1. Since ADR 0054 (private): `AgentSession.closeOpenGroups()` ends the run's open undo groups and forgets them (the groups now live in a field, not a run-local), so a tool provider that is about to dispose and rebuild schemes mid-run (a new Arduino driver adds node kinds) can call it and the next mutating call reopens a group lazily on whatever `Scheme` the resolver then returns — the session caches no `Scheme` across calls.
