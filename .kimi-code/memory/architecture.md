# Architecture

## Architecture

### `@falang/dto` — node model

The domain is a tree of typed nodes. `INode` is the runtime shape; `INodeConfig` is the _declaration_ of a node kind (name, optional zod `data` schema, children policy, mods/out flags, factory).

Children policy is one of:

- `children: true` — any node from the stack.
- `children: ['nameA', 'nameB']` — array whose members must be one of the listed names.
- `childTuple: ['header', 'body', 'footer']` — fixed positional tuple. Advanced TS types in `types.ts` (`NodeFromConfigItem`, `TupleChildren`, `NodesFromConfig`) derive a discriminated union of concrete node types from a config list.

Mods policy (ADR 0049 (private)) sits next to the children policy: `mods: ['timer']` on a host config lists the side-icon kinds allowed in that node's `mods[]` (declared with `modCfg`, at most one per kind per host; `haveMods` is deprecated). The union of all hosts' lists is `NodesStack.modKindNames` — mod-only kinds, never valid as a statement under `children: true`, enforced once in `createZodUnion` (`zod-mods.ts`).

Higher-level builders in `src/nodes/` (`action`, `cycle`, `ifCfg`, `switchCfg`, `functionCfg`) return arrays of `INodeConfig` representing a group of related kinds (e.g. `functionCfg` emits `function`, `function-header`, `function-body`, `function-footer`).

`NodesGroup` wraps a config list (`hasName`, `is`, `factory`, `getConfig`). `NodesStack` aggregates groups, enforces globally-unique names, and — crucially — builds a runtime `zod` discriminated union (`zod-utils.ts`) for `parseNode`/`parseDocument`. A missing/unknown child name at stack construction throws. When adding a new node config, wire its children names to entries that already exist in the same stack.

`defaultFactory` synthesizes a new node instance from an `INodeConfig` when the config has no custom `factory` — it is what `NodesStack.factory(name)` falls back to.

### `@falang/di` — DI tokens

Re-exports `tsyringe`, plus `createSchemeToken<T>(name)` (a branded `symbol`) and `resolveService(token, container)`. `reflect-metadata` is imported once here so consumers don't have to.

### `@falang/scheme` — editor runtime

Entry point: `schemeFactory({ infra, modules, document })` in `src/scheme/scheme-factory.ts`. It:

1. Creates a child `tsyringe` container off the root `container`.
2. Instantiates `Scheme` (`src/scheme/scheme.ts`) — holds the container, `SchemeInfrastructure`, MobX stores (`rootNode`, `icons`, `nodes`), the event bus, and the command bus.
3. If a `document` is passed, parses it through `infra.structure.parseDocument`, converts nodes into `NodeStore` instances via `createNodeStoreFromNode`, and syncs icons.
4. Registers base DI tokens (`TOKEN_SCHEME`, `TOKEN_CSS_CLASSES`, …) then calls `registerModules()` + `initializeModules()` on every passed `IModule`.

`SchemeInfrastructure` bundles a `NodesStack` with an icons-config map keyed by node name (shape, block view, icon config). The icons config comes from caller-provided React/emotion components under `src/shapes/` and `src/icons/`.

**Stores.** Observable state lives in MobX classes under `src/store/` and `src/scheme/`:

- `NodeStore` mirrors a DTO node with observable `data`, `meta`, `children`, `mods`, `out`, `parent`.
- `SchemeNodesStore` / `SchemeIconsStore` index nodes and icons by id.
- View-model stores (`SelectionStore`, `MousePositionStore`, `ViewPositionStore`, `BlockEditorStore`, etc.) are registered as container-scoped services and resolved via tokens in `di-tokens.ts` (or via the `useService(token)` React hook on top of `ContainerContext`).

**Actions → events.** Mutations live in `src/actions/` (`insertNode`, `deleteNode`, `moveNodes`, `setData`, `setMeta`, `setOutNode`). Each mutates stores inside `runInAction` (often implicitly through the command bus) and fires a typed event via `scheme.events.fireEvent(EVENT_*, payload)` from `scheme-events.ts`.

**Command bus with priorities.** `SchemeCommandsService` dispatches commands to listeners registered at five priority levels (0–4, high → low, see `TCommandListenerPriority`). A listener returning `true` stops propagation. This is how modules intercept or augment actions. Concretely, `dispatchCommand` drains priority 4 first down to priority 0 last, so a priority-4 listener always gets to intercept (and stop) before a default-priority (0) one runs — see `icons-transfer`'s own comment on this ("above … below") and the read-only guards below, which rely on it.

**Read-only mode.** `schemeFactory({ readOnly: true })` (or `new Scheme({ readOnly: true, ... })`) builds a scheme with `isEditing` observable starting `false`. This blocks: the inline editor (click/double-click no longer start editing, `init-editor-handlers.ts`), the icon/valence-point context menus (`register-context-menu-handlers.ts`), and the six mutation commands (`CMD_INSERT_NODE`/`CMD_DELETE_NODE`/`CMD_MOVE_NODES`/`CMD_SET_DATA`/`CMD_SET_META`/`CMD_SET_OUT`) via a priority-4 guard per command registered in `registerSchemeCommands` that returns `true` (stopping propagation) whenever `!scheme.isEditing`, so the real (default-priority) handler never runs regardless of registration order. Already-`isEditing`-aware code (`valence-points.service.ts`, `icons-transfer.service.ts`, `block-resize.service.ts`, `pseudo-block.cmp.tsx`, `skewer.cmp.tsx`) needed no change. Pan/zoom, selection (`focusNode`/`SelectionStore`), `CssClassesStore`, `ExecutionPositionModule` and `DebuggerModule`'s highlight all keep working — none of them go through the mutation commands. Every host's `*SchemeFactoryParams` (`functionalSchemeFactory`/`objectsStructureSchemeFactory`/`enumStructureSchemeFactory`/`externalApiStructureSchemeFactory` in `@falang/typescript-scheme`, `functionalSchemeFactory`/`mindTreeSchemeFactory` in `@falang/text-scheme`, `codeFunctionalSchemeFactory` in `@falang/simple-code-scheme`, `workflowFunctionalSchemeFactory` in `@falang/workflow-scheme`) already extends `Omit<ISchemeFactoryParams, …>` and forwards `...props` straight into `schemeFactory` — `readOnly` reached every one of them for free, no per-factory edit needed. See ADR 0025 (private) "Implementation notes (package B …)".

**First-child `out` is forbidden, everywhere** (ADR 0035 (private)). The visual language draws a skewer's `children[0]` continuing the enclosing scheme's main path straight down (`SkewerStore.isFirst`, starting `true` for every skewer and only ever cleared by `update-threads-child-positions.ts` for a non-first thread) — an `out` (break/continue/return/throw) there renders as `hasOutError`'s red box regardless of whether the parent is a branch, a plain sequential body, or a loop. `utils/can-have-out.ts`'s `canHaveOut(scheme, id)` is the one shared predicate (`false` when the node's own config has no `haveOut`, or when it's `children[0]` of its parent); `setOutNode` (`actions/set-out-node.ts`) throws when asked to _set_ (not clear) an out `canHaveOut` rejects. `if`/`while`'s own branch-direction flags (`IfIconStore.trueOnRight`/`WhileIconStore.trueIsMain`) are `@computed` getters over `dataNode.meta`, both defaulting `false` — matching every compiler's own default rather than the icon's old, disagreeing hardcoded `true`; a shared `utils/build-switch-true-false-menu.ts`'s `buildSwitchTrueFalseMenu` toggles the flag via `CMD_SET_META` (merging into existing `meta`, never replacing it). `IconStore.getMeta()` (previously registered but never called) now feeds `utils/get-dto.ts`'s `getNodeStoreDto`/`getDto` through a new optional `scheme` parameter, so an icon's computed meta default (e.g. `if`'s `trueOnRight`) is folded into the persisted DTO even for a node with no `meta` key yet — callers that still call `getNodeStoreDto` with one argument keep the old, defaults-free behavior.

**Pseudo-blocks** (`getPseudoBlockConfig`: `parallel`/`parallel-thread`, `pseudo-cycle`, `break`/`continue`, the text domain's `return`) draw only a bordered label (default cursor, no text selection) on `emptyShape`; `IBlockShapeConfig.ghostView` (set on `emptyShape` to the rectangle) is what the icons-transfer drag ghost draws for such shapes, otherwise the ghost would be invisible.

**Icons that hide their children** (ADR 0046 (private)): `IconFlags.HidesChildren` (`checker.hidesChildren`) makes `createIconForNode` skip every descendant's icon (the nodes still exist, compile and count for scope); `resolveVisibleIconId(scheme, id)` (`utils/resolve-visible-icon-id.ts`) returns the outermost ancestor whose icon hides its children, else `id`, and is used by `scrollToNode`/`focusNode`, `ExecutionPositionModule` and `DebuggerModule` so a run/pause/agent focus on a hidden node highlights and pans to the visible block. `SimpleIconStore`, `IconFlags`, `EDITING_INLINE_MODE_NAME`, `EditorService`, `BaseIconComponent` and `SchemeCommand` are now exported from the package index.

**Project module** (`src/modules/project/`) manages the project context within the editor — `ProjectService` holds the current project's id/name/type and a tree directory structure via `TreeDirectoryStore`.

**Debugger module** (`src/modules/debugger/`, ADR 0021) — `DebugSessionStore` is project-level (one per project, owns the `IDebugAdapter`, holds breakpoints keyed by document/node id — never in a node's `meta`); `DebuggerModule` is per scheme and takes that shared store plus the scheme's `documentId`, adding breakpoint dots (a scheme layer), a context-menu toggle (only if `ContextMenuModule` is present), `CMD_TOGGLE_BREAKPOINT`, and a `debug-current` block class + `scrollToNode` pan that follow the paused location. Breakable = `isStatementIcon` (parent has the `Skewer` flag). The antd panel lives in `@falang/antd`'s `ant-debug-panel`; hosts embed `DebugPanel` in their own right-hand `Sidebar`. Keyboard shortcuts and breakpoint persistence are host concerns.

**Version-diff module** (`src/modules/version-diff/`, ADR 0025) — `VersionDiffModule({ diff: INodeTreeDiff, side: 'left' | 'right' })` marks a static `@falang/versioning` diff onto one side of a split read-only diff view with `diff-added`/`diff-removed`/`diff-modified`/`diff-moved` block classes (green/red/amber/blue) via `CssClassesStore` — applied once in `initialize()` (the diff never changes across the module's lifetime; a new comparison builds a fresh pair of schemes), cleared in `dispose()`. `left` marks `removedIds`+`modifiedIds`+`movedIds`, `right` marks `addedIds`+`modifiedIds`+`movedIds` (a node both modified and moved gets both classes on its side). The pure helper `changeIdsForSide(diff, side)` returns the ordered, deduplicated list of ids worth stepping through (top-level removed/added plus every modified/moved id, in `diff.changes` order) for a "next/previous change" control built on the existing `scrollToNode`.

**Icons-transfer module** (`src/modules/icons-transfer/`, ADR 0027) — moving icons. Two gestures share one `IconsTransferService` (registered as an instance, it holds the `Scheme`) and one selection model (a contiguous range inside one `IIconWithList` parent, marked with the `selected` block class — deliberately not `SelectionStore`, which is the `focusNode` line-highlight selection): the click-based **transfer mode** (`DEFAULT_MODES.TRANSFER`: click an icon, a second click on the same skewer extends the range, click a valence point) and, in `start` mode, plain click / Shift-click range selection plus **drag-and-drop** (mouse-down on an icon, a move past `DRAG_START_THRESHOLD` enters the private `ICONS_DRAGGING_MODE_NAME` mode — registered without an icon, like `block-resize`'s — a `pointer-events: none` `IconsDragLayer` draws a dashed ghost of the selection + all descendants' shapes following the cursor, mouse-up drops onto `ValencePointsService.selectedValencePoint`). Both paths reuse `filterValencePoints` (installed as a valence-points filter) to decide where a drop is allowed and dispatch the same `CMD_MOVE_NODES` — `scheme.nodes`/`scheme.icons` are never touched during a drag. The command handlers (`init-icons-transfer-handlers.ts`) are thin wrappers around `mouseDown`/`mouseMove`/`mouseUp`/`mouseLeave`/`iconClicked`/`schemeClicked`, so `icons-transfer.test.ts` drives the service without a DOM. Requires `ValencePointsModule` on the same scheme.

**Copy-paste module** (`src/modules/copy-paste/`) — `new CopyPasteModule({ projectType, documentType, clipboard?, canPasteFrom? })`. "Copy" (`menu:copy`) in an icon's context menu copies the icons-transfer selection when the icon belongs to it, else just that icon — only regular children of a free list (`children: true` or a named list; never the root, a tuple slot such as `function-header`/an `if` branch, a mod or an `out`); the payload (`ISchemeClipboardPayload`: format `falang/scheme-nodes`, the project and document type, `toJS` snapshots of `getDto`) goes to an `ISchemeClipboard` — by default `defaultSchemeClipboard`, one in-memory clipboard per JS realm shared by every scheme of the window. "Paste" (`menu:paste`) appears on an `in-skewer`/`in-switch` valence point only when `CopyPasteService.canPasteAt` allows it: the scheme is editable, the origin matches (`canPasteFrom`, default = same project type and same document type), every node kind is known to the target stack, the parent's children policy accepts each top-level kind (`isAllowedChild` in `copy-paste.utils.ts`, mirroring `@falang/mcp-core`'s `getAllowedChildNames`: no document roots, mods, tuple slots or listed kinds such as `switch-option` in a statement body) and a node with an `out` doesn't land at index 0. `paste` replaces every id in the subtrees (children, mods, out — `cloneWithNewIds`, a nanoid-compatible `generateNodeId` over `crypto.getRandomValues`), so the same clipboard pastes any number of times, and dispatches one `CMD_INSERT_NODE` per node inside one `HistoryStore` group when `HistoryModule` is present. The service (`TOKEN_COPY_PASTE`, exported from the module file) works without `ContextMenuModule`/`IconsTransferModule` too. Hosts add it in their per-document scheme builders: `@falang/workflow-client-common`'s `buildWorkflowDocumentScheme` (project type `WORKFLOW_PROJECT_TYPE` = `'workflow'`, the document's type, `canPasteBetweenWorkflowDocuments` — same type, or `function` ↔ `trigger-function`, which share one stack), `@falang/desktop-agent-host`'s `buildSketchDocumentScheme` (only when `projectType` is passed — `DesktopProjectStore` passes its `falang.json` type; headless callers omit it) and `buildArduinoDocumentScheme` (always, `ARDUINO_COPY_PASTE_ORIGIN` = `arduino`/`function`). The magic node's popup scheme and read-only schemes don't get it. The clipboard is per window: a copy survives switching projects, and only the project _type_ is compared, so ids that point outside the subtree (a `call-function` target, an integration instance) are pasted as they are. Since 2026-11-10: `NodeStore` (constructor) and the `setData`/`setMeta` actions keep plain copies of `data`/`meta` (`utils/to-plain-data.ts`'s `toPlainData` — unlike MobX `toJS`, it also walks plain containers that hold observables): hosts build schemes straight from their deep-observable `documents` arrays, and the proxies used to reach the clipboard, where paste threw "Proxy object could not be cloned".

**Mods / side icons** (ADR 0049 (private)). A node's `mods[]` are ordinary nodes rendered beside their host through the normal `IconView`/`BlockView` path. The mod kind's icon config declares `mod: { placement: 'left' | 'right' | 'badge' }` (`sideIconConfig` builds it; `checker.isSide` flags it); only `left`/`right` count in layout — `IconStore.blockOwnLeft/blockOwnRight` (the host block alone) and `modsLeft/modsRight` (extra space for mods) feed the base `resetShape`, which places `SideIconStore` instances and draws the connector line to the host; `badge` is reserved. Loop heads (`foreach`/`while`) compute `left`/`right` from `blockWidth` themselves, so they add `modsLeft` explicitly (their return arrow already routes round `blockFullLeft`). `timerShape` is the first shape. `insertNode`/`deleteNode` take `slot: 'children' | 'mods'` (`TNodeSlot`, also on `EVENT_NODE_DELETED`), so history, read-only guards, sync and version diff come for free; `moveNodes`/`icons-transfer` ignore mods. `buildModsMenu` (shared) adds mods from the host's policy, `isIconDeletable` lets a side icon be deleted from its own menu.

**Validation module** (`src/modules/validation/`, ADR 0068 (private)) — `new ValidationModule({ validators?, queue? })`. A validator (`INodeValidator<TInput>`: `source`, synchronous `describe(node, ctx) → TInput | null`, `check(input, ctx) → issues` possibly async, optional `key(input)`) is run per node inside one MobX `reaction` over `describe`, so whatever `describe` reads (other nodes, registries) becomes its dependency; an input whose `key` (default `JSON.stringify`) is unchanged is never re-queued, `null` clears the source's issues. Validators come from the constructor and from `scheme.container.registerInstance(TOKEN_NODE_VALIDATORS, v)` made by other modules in `register()` (`resolveAll` in `initialize()`); a `validator?` on `IBlockConfig` is not supported. Nodes added/removed are followed through the new observable `scheme.nodes.ids`. Checks go through a `ValidationQueue` shared by the whole window (`defaultValidationQueue`; `setPriorityScheme(module.getSchemeKey())` for the active tab): FIFO, dedup by `(scheme, node, source)`, a version stamp drops results whose input changed meanwhile, bounded concurrency (default 1), `cancelScheme` on dispose, a throwing `check` is logged and counts as no issues, `idle()` for tests. Results live in `ValidationStore` (`TOKEN_VALIDATION_STORE`: `issuesFor(nodeId, field?)`, `hasErrors`, `hasWarnings`, `errorCount`, `warningCount`, `isPending`/`pendingCount`, `issuesByIcon`); issues are runtime state, never in `meta`. Display: block classes `has-error`/`has-warning` through `CssClassesStore` and a small hover marker layer (`ValidationLayer`, native `title` with the messages), both mapped through `resolveVisibleIconId`; read-only schemes show them too. A core layer `ValidationPill` (`data-testid="validation-pill"`, top-right corner of the scheme, hidden without issues, `validation:` locale keys en/ru in the core locales) shows "N errors" (or warnings) and each click pans to the next icon with an issue (`scrollToNode`; `orderIssueSites`/`pickNextIssueIcon` in `validation-pill.ts`: errors first, then top to bottom, cycling).

**History module** (`src/modules/history/`) is the canonical example of a module. It registers `HistoryStore` scoped to the container and subscribes to the mutation events to push inverse operations onto an undo/redo stack; `history.back()` / `history.forward()` replay them. Any new cross-cutting feature should follow this pattern: implement `IModule` (`register` for DI bindings, `initialize` for event/command wiring, `dispose` to clean up), then pass an instance via `schemeFactory({ modules })`.

**Icons / geometry.** `checker.ts` centralizes type-narrowing of icons by bitmask `IconFlags` (`isWithChildren`, `isWithSkewer`, `isCycle`, `isFunctionBody`, …). Layout code lives in `src/skewer/` (vertical chains), `src/threads/` (horizontal branching), and `src/shapes/` (SVG primitives).

**Test harness.** `packages/core/scheme/test-utils/` exposes `getTestInfrastructure()` + `getTestEmptyDoc()` — use these in new tests instead of rebuilding a stack from scratch. See `src/modules/history/history.test.ts` for the canonical setup pattern (`beforeEach` builds infra, calls `schemeFactory`, tears down with `scheme.dispose()`).

### `@falang/antd` — UI modules

Ant Design-based UI layer plugged into the scheme editor as modules. Key modules:

- `ant-context-menu` — context menu service and React layer, with handler registration via `register-context-menu-handlers.ts`.
- `ant-mods-selector` — the scheme's start/transfer mode switcher (bottom-left radio group; despite the name, not node mods). Hidden since 2026-10-05: `AntModsSelectorModule.initialize` no longer registers the layer (commented out), since drag-and-drop covers moving icons; transfer mode itself stays registered.
- `ant-resizable-panel` — `useResizablePanelWidth(storageKey, defaultWidth, { min, max, direction })` (drag-resize state, clamped, persisted to `localStorage` on pointer-up) + `ResizeHandle` (the thin draggable divider). Used by all three hosts (`packages/workflow/client-common`, `packages/desktop/app-arduino`, `packages/desktop/app-sketch`) to make the project-tree panel and the project-level right sidebar (agent chat/version history) resizable — each host keys its own two panels with `'falang:panel-width:project-tree'`/`'falang:panel-width:right-sidebar'`. The per-tab icon-editor column (`IconEditorColumn`/the old-`Sidebar`-equivalent) stays a fixed 350px, unaffected.

### Domain packages (`text`, `typescript`)

These follow the same `dto` + `scheme` pattern as core, adding domain-specific node definitions and block editors:

- `@falang/text-dto` / `@falang/text-scheme` — text-oriented nodes and block editors.
- `@falang/typescript-dto` — TypeScript-specific node configs (expressions, function calls, array operations, enums, external APIs, object definitions).
- `@falang/typescript-common` — shared input utilities used across TypeScript scheme blocks.
- `@falang/typescript-scheme` — TypeScript block configs for the scheme editor.

When adding new node configs in a domain package, reference them from the appropriate `NodesStack` and ensure their children names resolve to entries already on that stack.

### TypeScript scheme — `block-elements/` vs `blocks/`

`packages/typescript/scheme/src/block-elements/` holds small, reusable editing widgets (a MobX store + React component pair) shared across multiple node blocks — distinct from `src/blocks/`, which holds one full `IBlockConfig` per node kind. Most are internal (consumed via relative imports only, not exported from the package's `index.ts`) — the exception is `block-elements/code/`, see below.

- `block-elements/code/` — `CodeModelStore` (monaco `ITextModel` wrapper; supports a `hiddenPrefix` of lines hidden from the user but visible to the TS language service, e.g. scope `declare`s) — the hidden lines are ordinary model lines, so `CodeModelStore.setEditor` clamps every selection/cursor into the visible range (Ctrl+A, Ctrl+Home/End, drags), swallows Backspace/Delete at its edges, and rewrites the model from the last good value when an edit still damages the hidden prefix/suffix (pure helpers in `hidden-range-guard.ts`) + `CodeModelEditingComponent` / `CodeViewComponent` / `ExpressionEditorCellComponent`. `CodeModelStore` and `ExpressionEditorCellComponent` (plus `ExpressionBlockEditorStore` from `monaco/scope/` and `TsSelect` from `cmp/`) **are** exported from the package's `index.ts` — `@falang/workflow-scheme`'s `IntegrationActionEditorStore` (integration action node fields) consumes them across the package boundary to get real Monaco-backed expression fields and struct-aware selects, the same way any in-package block does. `monaco/get-monaco.js` (the shared Monaco accessor: lib variants, overflow-widgets host) and `monaco/use-code-theme.js` are exported the same way — `@falang/simple-code-scheme`'s `block-elements/raw-code/` (see "Simple-code domain" above) reuses them for its own, deliberately non-validating Monaco models instead of reimplementing Vite worker plumbing. **Monaco is host-installed (ADR 0051 (private), headless-scheme seam):** `get-monaco.ts` has no runtime import of `monaco-editor`, no `?worker`, no CSS and no module-scope `self` — `getMonaco()` throws a clear "Monaco is not installed" error until `installMonaco(monaco, { getWorker })` has run, and the package index stays importable (and every scheme factory usable) in plain Node via `npx tsx`. Browser hosts install it by importing the browser-only module once from their entry file — `import '@falang/typescript-scheme/src/browser.js'` (static `monaco-editor` import, the Vite `?worker` TS worker, `monaco-styles.css`, `prism-styles.css` and the two Prism theme stylesheets via `installPrismThemes`); it is deliberately **not** re-exported from the package index. Every host that builds Monaco-backed schemes must import it: the workflow client (`render-workflow-app.tsx`), `app-sketch`/`app-arduino` (`renderer/src/main.tsx`) and both playgrounds. `@falang/simple-code-scheme/src/browser.js` (imports the typescript one, then installs the `monaco-editor/esm/vs/basic-languages/{typescript,javascript}` tokenizers via `installCodeLanguageTokenizers`) and `@falang/text-scheme/src/browser.js` (the Lexical block's `html-block.css`) follow the same pattern; `app-sketch` imports all three. The smoke test is `npm run test:headless-schemes` (`scripts/headless-scheme-smoke.ts`: builds every product's real scheme factory in plain `tsx`, inserts a node through the command bus, serializes with `getNodeStoreDto` and validates with `@falang/mcp-core`'s `validateDocument`; a root `tsconfig.json` exists only so `tsx` run from the repo root applies `experimentalDecorators`). Note `getNodeStoreDto` omits falsy `data` and empty `children`, so its raw output is not re-parseable by the strict stack validators on its own. `getMonaco()` also exports `setMonacoLibVariant('full' | 'portable', extraDeclarations?, extraLibFiles?)` (`extraLibFiles`: whole files by path, e.g. a package's `.d.ts` under `file:///node_modules/<pkg>/` — the workflow client's `dayjs`; counted in `getMonacoLibKey` by a version number) — `monaco.typescript.typescriptDefaults` is one global instance for the whole window, so which `lib.d.ts` every `'typescript'`-language model type-checks against is a host-level choice (call once per opened project, before building its schemes), not a per-editor one. `'full'` (the default) is TypeScript's own `lib.esnext.d.ts` from the Monaco TS worker's bundled lib files, set as compiler option `lib: ['lib.esnext.d.ts']` (compiler options take lib _file_ names — the tsconfig short form `'esnext'` loads nothing; no DOM) — until 2026-11-10 it was a hand-copied `lib.es5.d.ts` (`monaco/lib.ts`, deleted), so `startsWith`/`includes`/`Map`/`Object.entries` were missing from completions and flagged as errors although the backend type-check (esnext) accepted them; `'portable'` switches the options to `noLib: true` and adds `lib-portable.ts` as an extra lib. `'portable'` (`monaco/lib-portable.ts`) is a hand-written, deliberately minimal replacement declaring only what `@falang/logic-constructor`'s `cpp`/`golang`/`rust`/`sharp` adapters actually support (see ADR 0019 (private)) — `Math` trimmed to the 9 methods every adapter's `CALL_MAP` whitelists, `Array`/`String` trimmed to `length`+indexing, no `Promise`/`JSON`/`RegExp`/`Symbol`/`Map`/`Set`/`Date`/free functions at all — so the editor never suggests or accepts syntax that would only fail later with `UnsupportedConstructError` at export. `@falang/desktop-app-sketch`'s `DesktopProjectStore` selects `'portable'` for `project.type === 'logic'` (`'full'` otherwise) and `@falang/desktop-app-arduino`'s `ArduinoProjectStore` always selects `'portable'` (every Arduino sketch compiles to C++ only, through the same `@falang/logic-constructor` statement compiler); the workflow product never calls it, staying on `'full'`, since its `function`/`trigger-function` documents compile to real, executed TS. `setMonacoProjectDeclarations(text)` (2026-11-08) is a separate, frequently replaced extra lib (`@types/lib-project.d.ts`) for the open project's own ambient names (the workflow product's constants); it bumps an observable counter inside `getMonacoLibKey()`, and the TypeScript fields validator's `key` includes that key, so every field is re-checked when the declarations change.
- `block-elements/new-variable/` — `NewVariableStore`, a plain text input (no monaco) for fields that _declare_ a new identifier rather than an expression. Validates TypeScript identifier syntax and rejects reserved words (`validate-variable-name.ts`), and checks uniqueness against a caller-supplied `getScopeNames()` callback (typically `collectScopeVariables(dataNode).map(v => v.name)`).

### TypeScript scope tracking (`monaco/scope/`)

- `collectScopeVariables(node: NodeStore): IScopeVariable[]` now lives in `@falang/typescript-common` (`src/scope/collect-scope-variables.ts`, moved there per ADR 0009 so it's importable from node tests without pulling in `monaco-editor` through `@falang/typescript-scheme`'s index); `packages/typescript/scheme/src/monaco/scope/collect-scope-variables.ts` is kept as a one-line re-export so existing in-package imports are unchanged. It walks up from a node, collecting every scope-introducing sibling declared _before_ it in each enclosing scope: `create-var` (explicit `TVariableInfo`), plus the array ops that assign a result — `arr-pop`/`arr-shift` (new variable typed as the array's _element_ type) and `arr-slice` (new variable typed as the _array_ type itself). The latter two only know a raw `typeof`-based type query, not a structured DTO type, so `IScopeVariable['type']` is `TVariableInfo | IRawVariableType` (`{ type: 'raw', expression, constant? }`, see `scope-variable.ts`); `build-hidden-scope-code.ts` renders a raw type verbatim instead of running it through `variableInfoToTsType`.
- `array-element-type.ts` builds those raw type queries from an `arr`-field's expression text: `buildArrayTypeExpression('someobj[x+1].someArr')` → `"typeof someobj[number]['someArr']"` (dots become `['prop']`, bracket contents become `[number]` — verified against `tsc`: TS's `typeof` type-query grammar disallows a dot immediately after a bracketed index). `buildArrayElementTypeExpression` appends one more trailing `[number]` to peel the array type down to its element type.
- `buildHiddenScopeCode(variables, typesRegistry)` renders `collectScopeVariables`'s output into `declare const/var …` lines prepended (invisibly, via `hiddenPrefix`) to a monaco model; struct types are resolved from `TypesRegistryStore` and emitted as `interface` declarations.
- The array-op node blocks were split by whether they need a value typed in or produce one: `arr-op-returning` (arr-pop, arr-shift — result field uses `new-variable`) and `arr-op-input` (arr-push, arr-unshift — value field uses `code-model`, hidden-prefixed with the array's element type) replaced the old single `arr-op` block. `arr-insert`'s `insertArr` field is hidden-prefixed with the array's own type (matching element type, since the items are spread in).
- **Fixed bug (2026-10-04)**: `call-function`/`call-api`'s `returnVariable` never reached a later sibling's Monaco scope ("Cannot find name" in a `logic` project after assigning a function call's result) — the target's return type lives in a per-project registry (`TypescriptProjectService.functionsRegistry`/`externalApiRegistry`, keyed by `schemeId`/`iconId`), which `@falang/typescript-common` can't see and the global `registerScopeContributor`/`SCOPE_CONTRIBUTORS` registry isn't safe for (a per-project lookup would collide across concurrently open projects sharing one process — see `node-scope-contribution.ts`'s existing integration-action contributors, which only register state-independent contributors for exactly this reason). Fixed with an optional `resolveExtra: TScopeContributionResolver` second parameter on `collectScopeVariables` — consulted per sibling only when `SCOPE_CONTRIBUTORS`/`dynamicScopeContributors` contributed nothing for it — wired up in `ExpressionBlockEditorStore` (`expression-block-editor.store.ts`), where `this.projectService` already gives safe, container-scoped (not global) access to those registries. Every block extending `ExpressionBlockEditorStore` (action/if/create-var/log/return/arr-\*/call-function/call-api/foreach-header/from-to-cycle-header, plus workflow's integration-action/-choice/activepieces-action blocks) gets this for free.
