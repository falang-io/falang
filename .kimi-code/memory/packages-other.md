# Simple-code, standalone services, playground, and site

**Simple-code domain** (`packages/simple-code/`) — the third `packages/desktop/app-sketch` project type (ADR 0024 (private)): raw, per-language source text edited with syntax highlighting only (no parsing/validation), compiled by simple string-concatenation codegen:

- `dto` — `@falang/simple-code-dto`: `codeFunctionNodesGroup`, built entirely from `packages/core/dto/src/nodes/`'s generic builders (`action`/`ifCfg`/`switchCfg`/`cycle`/`pseudoCycleCfg`/`functionCfg`) — every field is one shared raw-string `codeDataType`. `languages.ts` holds `TCodeLanguage` (`cpp`/`js`/`ts`/`php`/`rust`) and the `DocumentType ⇄ language` mapping.
- `scheme` — `@falang/simple-code-scheme`: `codeFunctionalSchemeFactory({..., language})` reuses `@falang/typescript-scheme`'s generic icon-config helpers (if/switch/foreach/while/function/pseudo-cycle) as-is, pairing them with one language-parametrized Monaco block (`blocks/raw-code/`) reused for every field. `block-elements/raw-code/`'s `RawCodeModelStore` deliberately does not reuse `@falang/typescript-scheme`'s `CodeModelStore` — that one is hard-wired to the real, always-validated `'typescript'` id. `ts`/`js` get private monaco language-id aliases (`monaco-languages.ts`) so the shared strict TypeScript worker (configured by `@falang/typescript-scheme`'s `getMonaco()`, now also exported for this reuse; the `ts`/`js` Monarch tokenizers are host-installed through `@falang/simple-code-scheme/src/browser.js`, so the package index has no runtime `monaco-editor/esm/...` import) never attaches diagnostics to raw `simple-code`-domain fragments; `cpp`/`php`/`rust` use their real monaco ids directly (no language service attached to them anywhere in this codebase).
- `export` — `@falang/simple-code-export`: `generateCode(root, language)` walks an `INode` tree with a small ported `CodeBuilder` (indent-tracking string accumulator) — no TS Compiler API, unlike `@falang/logic-constructor`. `exportCodeProject` compiles every `simple-code-*` document (one document = one output file) and writes to `<projectDir>/generated/`. Corrects several real bugs found in the old app's own per-language generators (doubled/skipped function header-footer emission, invalid Rust `switch` syntax, dead `_continueValue`/`_breakValue` machinery) rather than porting them — see the ADR. Since ADR 0035 (private): `generators/shared.ts`'s `resolveWhileCondition` (one shared copy, reused by all five language generators, unlike `@falang/logic-constructor`'s per-target copies) negates a `while`'s condition when `meta.trueIsMain === true`, matching `resolveIfBranches`'s existing `meta.trueOnRight` convention.

**Standalone services outside the workspace**:

- `proxy/` — `falang-proxy` (ADR 0056 (private)): a zero-dependency HTTP forward proxy (`CONNECT` tunnels plus absolute-URI HTTP; `Proxy-Authorization` Bearer or Basic with a token from `PROXY_TOKENS`, `PROXY_ALLOWED_PORTS` default `443,80`, `GET /health`, `PROXY_EXPOSE_STATS` for e2e) that an administrator runs in another region so selected integrations can reach APIs unreachable from the platform's own. Own `package.json`/lockfile/`Dockerfile`, like `activepieces/` (the ActivePieces adapter service, see ADR 0010 (private)); not an npm workspace member, so the root `npm test` does not run it.

**Playground** (`playground/`):

- Vite + React harness for manually exercising the libraries (`"type": "module"`).

All packages publish from `src/index.ts` (no build step is required to consume them in-repo — `main` points straight at TS source).

**Public site** (`site/`) — not a package, not an npm workspace member: two sibling standalone Astro projects, each with its own `package.json`/lockfile, sharing no code with the rest of the repo or with each other. Originally one project migrated from the old Express/Nunjucks site (`old/packages/site/web`); split in two the same day once a docs redesign turned into a Starlight migration, since Starlight's sidebar/search/routing assume it owns a site's routing from the root and can't be nested under a path prefix alongside a separately-routed homepage — see ADR 0016 (private) "Implementation notes (Phase 3, `falang.ru`)" section (both the initial migration and the same-day split/Starlight-autogenerate gotcha) for the full history.

- `site/main` — the marketing home page, plain Astro (no Starlight/MDX), Blueprint-styled (unchanged since the original migration). One codebase, two locale builds selected at build time via `SITE_LOCALE` (`dist/en` → `falang.io`, `dist/ru` → `falang.ru`). See its own README, including a real Astro gotcha hit along the way (`<title>` mis-parses more than one `{}` expression inside it and leaks the rest of `<head>` into `<body>`; build the title as a single string instead).
- `site/docs` — the docs site, [Astro Starlight](https://starlight.astro.build) (search, TOC, responsive sidebar out of the box), same `SITE_LOCALE`-per-build model as `site/main` but on its own domain (`docs.falang.io` / `docs.falang.ru`, cross-linked from/to `site/main`'s nav — see its own `Header.astro`/`Nav.astro`). See its own README for the content layout (`.mdx` + `ImageRow`/`Gallery` components) and why its sidebar uses manual `slug` entries instead of `autogenerate` (a Starlight gotcha with per-locale content directories — `autogenerate` matches by on-disk file path against a hardcoded `src/content/docs`, oblivious to this collection's locale-scoped loader `base`, so autogenerated groups silently rendered empty).

Both require Astro `^7.3.2` (upgraded from `^5.16` the same session — the latest Starlight needs Astro `^7.2.10`) and ship independently of the k8s workflow-product stack, per ADR 0016 (private) `falang.ru` bullet.
